# Onalign 기획서 (Draft v30 — 문서화·녹음·프롬프트 고도화 제안)

> **문서 성격**: 외부 마감 없는 개인 프로젝트. "빨리 내놓는 것"보다 "정확히 짚었는가"가 기준.
> **서비스명**: Onalign 확정, https://onalign.vercel.app 배포 완료
> **이 문서의 독자**: 본인 — 의사결정자 겸 실행자를 겸함. 그래서 "누구를 설득할 근거"보다 "다음에 뭘 할지 스스로 판단할 근거"가 우선이다.

## 0. 요약

> ### ✅ 확정 (v28): 익명 참여 폐지, 전원 구글 로그인 방식으로 간다
> v26에서 제기했던 질문(팀원 익명 참여 폐지가 의도한 방향인가)에 대해, 랜딩페이지를 로그인 전제로 다시 써달라는 이번 요청으로 답이 확인됐다. **이제부터 "참여자는 로그인 없이 이름만 입력"이라는 기존 전제는 폐기하고, "리더든 팀원이든 구글 계정으로 로그인해야 참여 가능"으로 문서 전체를 갱신한다.** 4장 차별점 1번, 11장 경쟁사 포지셔닝, 랜딩페이지 카피를 이번 버전부터 이 전제로 정리했다.

### 왜 (Why) — 문제와 근거
캠프 아이디어 회의에서 "문제 정의" 단계에 가장 많은 시간을 쓰고, 그마저도 서로 다른 말로 같은 문제를 가리키는 걸 못 알아채 회의가 길어지는 걸 직접 관찰했다. 근거는 세 겹이다 — 본인 관찰(1차), production blocking 등 심리학 이론(보조), 노션 동시편집 데이터 유실 경험(가장 구체적, 엔지니어링적 사실). 외부 회의 비용 통계(연 392시간, 67% 비생산적)와 캠프 KPT 회고 11개 팀 실제 사례로 추가 검증했다(10, 14장).

### 무엇 (What) — 지금 만들고 있는 것
5~15인 소규모 팀을 위한, **구글 계정으로 로그인해 참여하는** 퍼실리테이션 도구(v28부터 "로그인 없이"에서 전환). 의견 작성 → 문제 정리 → 우선순위 투표 → **회고(KPT)** → **문서화**까지 한 프로젝트 안에서 이어진다. 메인 경쟁자는 EasyRetro/TeleRetro이며, 이들과 달리 "아이데이션과 회고를 잇는다"는 게 가장 방어력 있는 차별점이다(3, 4장). "로그인 없음"은 더 이상 차별점이 아니게 됐다 — 대신 "링크 하나로 전원이 같은 흐름에 올라탄다"는 쪽으로 포지셔닝을 옮긴다.

### 어떻게 (How) — 지금까지 만든 것과 확정된 설계
- **구현 완료 (배포·검증 완료)**: 의견 작성(다중 보드, 병합, 보류함, 빈공간 클릭 생성), 문제 정리, 우선순위 투표, 회고 탭, 문서 탭(표준 4필드, docx/프롬프트 추출, 녹음→녹취록 반영·경합버그 수정), 정렬 기준 통일
- **구현 완료 (v29 — 배포 완료 확인)**: 구글 로그인, 팀원 로그인 필수화, 공유 링크(`?p=id`), 리더 권한 분리(STEP 배너·투표권 수정·프로젝트 삭제=오너 전용), 헤더 배지 통합 — **실제로 커밋·push되어 배포 완료.** 랜딩페이지도 fetch로 실사이트 반영 직접 확인함(13장)
- **랜딩페이지 v28 개편**: 로그인 전제 반영, 4단계→5단계 흐름도 확장(회고·문서화 추가), 프롬프트 추출 신규 소개 섹션 (아래 참고)
- **의도적으로 미룸**: GitHub 로그인(구글 정상 확인 후 추가 예정), 수익화(6장)
- **알면서 택한 트레이드오프**: 투표는 익명 대신 상시 실명(11-3장)
- **설계 원칙**: "개인 화면 상태 vs 공유 데이터 분리"(13-10)

### 아직 열려 있는 것
1. **5~8인 규모에서 동시 작성이 실제로 효과 있는가** — 학계도 결론 없음(11-1)
2. **회고가 실제로 팀에 도움이 되는가** — 실증 연구 자체가 얇음(11-2)
3. **문서 표준 4필드 편집 권한**(참여자 누구나로 제안, 미확정 — 6-1장)
4. **이름 배지가 프로필 사진처럼 둥글게 보이는 현상** (원인 미특정, 캐시 의심 — 13-10)
5. **로그인 없음 포기에 따른 재검증 필요**: 12장 설문 가설 A("로그인 없는 참여가 세션 시작률을 높인다")는 이제 이 서비스에 적용 안 되는 가설이 됨 — 폐기하거나 "구글 로그인 마찰이 참여율에 영향 주는가"로 재작성 필요

### 다음 액션 (지금 할 수 있는 것 순서대로)
1. 온보딩 투어 정책 변경(계정당 1회) 실사용자 계정으로 재확인
2. 이름 배지 둥근 표시 이슈 하드 리프레시로 재확인 (여전히 열려있는 항목 4번)
3. 12장 설문 가설 A 재작성 후 배포 (캠프 내부+외부 최소 15~20건)
4. 사전 판단 기준(12장)과 응답 대조, 유리하게 재해석하지 않기

### ✅ 로그인 착수 전 체크포인트 (v22)


로그인처럼 파급력 큰 변경에 들어가기 전, 그 이전까지 나온 기능들이 전부 매듭지어졌는지 확인했다. 아래 세 가지는 **열린 질문 없이 완전히 확정된 상태**다.

- 보류함(파킹랏) — 구현 완료
- 프로젝트 목표 한 줄 고정 — 구현 완료
- 회의 녹음 → 텍스트 변환 — 구현 완료, 목적·권한·비용구조·제약까지 전부 확정 (5-2, 13-4, 15장)

이 체크포인트 이후에 들어가는 변경(로그인, owner_id, 권한 분리)부터는 "이미 안정된 기능 위에 얹는 것"이라는 전제로 진행한다.

## 1. 문제 정의

**결론: 문제는 "발언 부족"이 아니라 "서로 다른 말로 같은 문제를 가리키는 걸 못 알아챔"이다.**

- 출발점: 시장조사가 아니라 캠프 아이디어 회의 관찰
  - 시간 대부분을 "문제 현상/문제 정의"에 씀
  - 상대 의도를 못 알아채 회의가 길어짐
- 기존 워크플로우("의견 → 병합 → 문제 정리")와의 정합성 확인
  - 원래도 "의도가 겹치는 의견을 눈에 보이게 모으는" 구조였음
  - 풀어야 할 병목은 "말 못 함"이 아니라 "수렴 안 됨"

**근거 축 3가지 (우선순위 순)**

1. **본인 관찰** (1차 근거) — 캠프 회의에서 직접 겪음
2. **외부 조사** (보조 근거) — 직장인 약 절반이 침묵, 원인은 두려움보다 무력감
3. **노션 동시편집 버그** (가장 구체적, 신규) — 같은 자리 동시 편집 시 데이터 유실 경험
   - 포스트잇마다 편집 영역 분리 → 동시 충돌 원천 차단
   - 심리학 이론과 무관한 엔지니어링적 사실, 논문 불필요

**+ 독립 설계 목표**: "재미있게" — 생산성 축과 무관, 10~11장 학술 근거로 정당화/반박 대상 아님

> **정확히 하자면**: 실제 구현은 완전 독립 저장이 아니라 "최신 상태 재조회 후 내 항목만 반영" 방식 — 충돌 확률을 낮추는 것이지 원천 차단은 아님. 과장 금지.

**가설 1 (재수정)**
> 포스트잇 분리 시 (a) 동시편집 데이터 유실 방지 [사실에 가까움] + (b) 의도 파악 실패로 인한 지연 감소 [검증 필요]

**남은 숙제**: 지금의 "병합"은 누군가 먼저 "같은 얘기다"라고 알아채야 작동 → "알아채지 못하는 순간" 자체는 못 없앰 (5장 이후 계속)

## 2. 목표 사용자

**결론: 1차 타깃은 이미 문제를 겪고 있는 게 확인된 집단(캠프/부트캠프)이다. 시장 검증된 타깃이 아니다.**

- **1차 타깃(확정)**: 캠프·부트캠프의 5~15인 소규모 팀
  - "문제 현상 정의" 단계에 시간 최다 소요 + 의도 불일치 경험 그룹
  - 10장("첫 실사용자 = 본인 팀")과 정확히 일치
- **2차 확장 타깃(v1 범위 밖)**: 프로덕트/디자인 팀, 애자일 코칭 조직
  - 전제조건: 아이디어 회의 자체를 이 도구로 진행 — **미검증**

## 3. 경쟁 환경 분석

**결론: EasyRetro/TeleRetro가 메인 경쟁자다. "아이데이션-회고 연결"을 가볍게 제공하는 도구는 없다.**

**시장 카테고리**: "Brainstorming Software" ↔ "Retrospective/Agile Facilitation Tools" 사이 (후자에 더 가까움). 두 카테고리에 걸쳐 있다는 것 자체가 4장 핵심 차별점.

| 도구 | 성격 | 강점 | 약점(기회) |
|---|---|---|---|
| EasyRetro | 회고 전용, 링크 참여 | 가볍고 무료, 템플릿 250개+ | 세션 간 연결 없음 (킥오프-아이데이션 미연결) |
| TeleRetro | 회고 전용 + 펄스 서베이 | 세션 사이 팀 상태 추적 가능 | 연결이 "분위기"에 한정, 목표·우선순위와는 무관 |
| ClickUp/monday/Notion (참고) | 범용 업무관리 + 회고 템플릿 | 회고-작업(Task) 연결 가능 | 무겁고, 워크숍 특유의 동시작성 경험 약함 |

**핵심 발견**: 아이데이션(시작 시점 우선순위)과 회고(종료 시점 회고)를 같은 프로젝트 안에서 가볍게 잇는 도구 = 조사 범위 내 없음 → 5장 근거

**기타 확인 사실**
- 투표 기능(익명·인당 제한·자동집계) 불만이 FigJam 커뮤니티에 반복 제기
- 협업 화이트보드 시장: 20억~45억 달러(2025~26), 연 12~20% 성장 — 단, 범용 시장 수치이며 회고 전용 소도구 시장 크기는 자료 없음

## 4. 차별점 (가치 제안 가설)

**결론: 5가지 차별점 중 방어력이 가장 큰 건 "아이데이션-회고 연결"이다. 1번은 v28에서 로그인 필수 전제로 재작성됨. 전부 미검증 가설이다.**

| # | 차별점 | 핵심 |
|---|---|---|
| 1 | ~~오너는 계정, 참여자는 이름만~~ → **전원 구글 로그인, 링크 하나로 즉시 합류 (v28 수정)** | 참여 마찰은 "로그인 없음"이 아니라 "회원가입 절차 없이 계정 하나로 바로 합류"로 재정의. 영구 기록(6장)은 계속 유지 |
| 2 | 하나의 흐름에 특화 | 의견→병합→문제정리→투표→회고→문서화 강제, 산으로 안 감 |
| 3 | 프로젝트별 저장/재방문 | 회고는 반복 행위 — 이력이 쌓이는 구조 |
| 4 | 문서화(docx/마크다운/이미지) + 프롬프트 추출 | 별도 정리 작업 없이 문서화, AI 요약은 사용자가 이미 쓰는 AI로 위임 |
| 5 | **아이데이션-회고 연결** | 시작 때 우선순위를 종료 시 회고에서 재확인 — **방어력 최대** |

⚠️ **주의**: "로그인 없음"이 사라지면서 EasyRetro/TeleRetro 대비 마찰 비교 우위도 재검토가 필요하다 — 이 두 경쟁사는 지금도 로그인 없이 참여 가능하므로, 이 항목에서는 오히려 Onalign이 더 무거워진 셈이다. 이건 11장에서 다시 다뤄야 할 사항이다.

## 5. 신규 기능 설계: 아이데이션 → 회고 연결

**결론: "회고" 탭이 5번째 탭으로 상시 존재하고, 참여자 각자 KPT를 작성·완료하며, 완료할 때마다 그 사람 몫이 문서 탭에 반영된다. 우선순위 해결여부 체크는 토글로 켜고 끌 수 있다. (v18, 확정 — 5장 설계 완료)**

1. 탭 구성: 의견 작성 → 병합 → 문제 정리 → 우선순위 결과 → **회고** (5개 탭 상시 노출, 이전 설계의 "완료 버튼으로 잠금 해제" 방식에서 단순화됨)
2. 회고 포맷: KPT (Keep-Problem-Try), 참여자 수만큼 입력 칸 제공 — **누가 작성했는지 이름과 함께 표시** (실명, 병합/문제 등 다른 기능과 일관된 방식)
3. "완료" 버튼: **참여자 개인 단위** — 팀 전체를 기다리는 게이트 없이, 각자 자기 KPT를 다 쓰면 자기 버튼만 누름 → 그 사람 몫이 "과정 문서"와 "결과 문서" 양쪽에 반영됨. 완료 후에도 **잠금 없이 자유롭게 재수정 가능**
4. **우선순위 해결여부 체크 (토글, 확정)**: 회고 탭 상단에 ON/OFF 토글 스위치
   - ON: 아이데이션 우선순위 상위 문제 목록 + 해결됨/부분해결/미해결 체크 섹션이 참여자별 KPT 입력칸 위에 표시
   - OFF: 이 섹션 없이 KPT 입력칸만 표시
   - 기본값: **ON** (핵심 차별점 요소이므로 기본 노출, 문제 정의로만 끝난 프로젝트는 팀이 직접 꺼서 숨김)
   - 토글 권한: 참여자 누구나 (되돌리기 쉬운 화면 설정이라 리더 전용 아님)
   - 근거: "이 회의가 문제 정의만 할 예정이었는지, 해결방안까지 도출하는지는 팀마다 다르다"는 판단 — 강제 노출이 아니라 선택 가능하게 둠

**의도적 제외**: 액션 아이템 담당자·마감일·Jira 연동 → ClickUp/monday 영역, 체급 밖

### 확정 이력

| 질문 | 결론 |
|---|---|
| 우선순위 문제 자동 표시 + 해결여부 체크를 회고 탭에 유지할지 | ✅ 유지, 단 ON/OFF 토글로 (기본 ON) |
| "완료" 버튼 권한 | ✅ 참여자 개인 단위, 팀 전체 게이트 없음 |
| "완료" 후 개별 KPT 재수정 가능 여부 | ✅ 잠금 없음, 언제든 자유 수정 |
| 프로젝트 상태(`진행중`/`완료`) 필드를 별도로 둘지 | ✅ 제외 — 완료가 개인 단위라 불필요 |

### 5-1. 문서 탭 표준 항목 추가 (v16, 신규)

**결론: "과정 문서"·"결과 문서" 둘 다 목적/배경/추진방향/기대효과 4개 필드를 공통으로 갖고, 인라인 편집 가능해야 한다.**

| 필드 | 적용 대상 | 비고 |
|---|---|---|
| 목적 | 과정 문서 + 결과 문서 공통 | 인라인 편집 |
| 배경 | 과정 문서 + 결과 문서 공통 | 인라인 편집 |
| 추진 방향 | 과정 문서 + 결과 문서 공통 | 인라인 편집 |
| 기대 효과 | 과정 문서 + 결과 문서 공통 | 인라인 편집 |

- 기존 콘텐츠(과정 문서: 개요·참여자·의견모음·문제정리 / 결과 문서: 개요·우선순위 TOP5)는 이 4개 필드 아래에 이어지는 구조로 배치
- **내보내기 형식(v23 변경)**: HTML 다운로드 → **docx(Word) 다운로드**로 교체. 마크다운/이미지 내보내기는 유지. 이 4개 필드는 세 형식 전부에 포함
- 4개 필드는 프로젝트 단위로 한 번만 입력하면 과정/결과 문서 양쪽에 동일하게 반영 (별도로 두 번 입력하지 않음)

### 5-3. 프롬프트 추출 기능 (v23, 신규)

**결론: 문서 탭에 "AI 요약" 기능을 직접 만드는 대신, 사용자가 이미 쓰는 AI에 붙여넣을 프롬프트만 만들어준다 — 서버 비용 없음.**

- **배치**: "마크다운으로 다운로드" 버튼 옆에 "프롬프트 추출" 버튼 추가
- **동작**: 클릭 시 문서 표준 4필드(목적/배경/추진방향/기대효과) + 의견 모음/문제 정리(또는 결과 문서라면 우선순위 TOP) + **회의 녹취록**을 하나로 합치고, 맨 앞에 "다음 회의 자료를 바탕으로 정리된 문서를 작성해줘" 류의 지시문을 붙인 완성된 프롬프트 텍스트를 생성
- **출력 방식**: 클립보드 복사 버튼 (붙여넣어 바로 쓰는 용도이므로 다운로드보다 복사가 우선)
- **설명 가이드**: 버튼 근처에 짧은 안내 문구 필요 — 예: "회의 녹취록과 문서 내용을 하나의 프롬프트로 만들어드립니다. 복사해서 ChatGPT·Claude·Gemini 등 사용하시는 AI에 붙여넣으면 정리된 문서를 받아볼 수 있습니다."
- **설계 원칙과의 일관성**: 이건 5-2장(녹음 기능을 Whisper 유료 API 대신 무료 Web Speech API로 최종 확정)과 같은 결의 선택이다 — AI 요약이라는 기능 자체는 제공하되, 그 연산 비용은 서버가 아니라 사용자가 이미 보유한 AI 계정으로 넘긴다. 이 프로젝트가 "무료로 최대한 간다"는 원칙을 로그인 이전 마지막 기능에서도 그대로 지킨 셈이다

### 5-2. 녹음 → 문서 보강 연동 (v16, 신규) — 무료 구현 가능성 검토

**결론: 텍스트를 문서에 넣는 것 자체는 무료로 가능하다. 다만 무관한 두 가지 무료 티어 리스크가 있다.**

- 텍스트 이관 자체: 추가 비용 없음. 텍스트는 용량이 작아 Supabase 무료 DB(500MB)로 충분
- ⚠️ **기기 커버리지 리스크**: Web Speech API는 Chrome/Edge 데스크톱에서만 안정적. iOS Safari 등 모바일 브라우저는 지원이 불안정하거나 미지원 — 참여자 일부 기기에서 녹음 자체가 안 될 수 있음
- ⚠️ **Supabase 무료 티어 운영 리스크(녹음과 무관, 프로젝트 전체에 해당)**: 7일간 DB 요청 없으면 프로젝트 자동 일시정지(2026년 기준 여전히 유효). 캠프 세션 사이 간격이 있는 사용 패턴이라 실제로 겪을 수 있음 — GitHub Actions 등으로 주기적 핑을 보내는 무료 우회책 존재

### 5-4. 리스트 정렬 기준 정리 (v24, 신규)

**결론: 세 화면(문제 정리 탭, 우선순위 결과 탭, 문서 출력)의 정렬 기준이 서로 다르게 필요하다. 하나는 버그 의심, 하나는 신규 결정.**

| 화면 | 원래 설계 | 현재 상태(보고됨) | 처리 방향 |
|---|---|---|---|
| 우선순위 결과 탭 | 득표순 내림차순, 1위 강조(7장 기능명세서에 이미 명시) | 작성순으로 보임 | ⚠️ **설계와 다르게 동작 — 버그 의심.** 새 결정이 아니라 원래 설계대로 고치는 작업 |
| 문제 정리 탭 | (정렬 기준 없었음) | 작성순 | **신규 결정 필요**: 득표수 내림차순 우선, 표가 없는 항목끼리는 "문제로 표시된 시점" 최근순으로 제안(확인 대기) |
| 문서 출력 | 없음 (각 탭 순서를 그대로 따른다고 암묵적으로 가정) | 미확인 | 결과 문서는 우선순위 결과 탭과, 과정 문서의 문제 정리 표는 문제 정리 탭과 동일한 순서를 따르도록 명시 |

⚠️ **확인 필요**: 문제 정리 탭에서 무표 항목끼리의 2차 정렬 기준을 "문제로 표시된 시점(최근순)"으로 제안했는데, 이게 맞는지, 아니면 "원본 포스트잇 작성 시점"이 더 나은지 확인 필요.

## 6. 계정 시스템과 데이터 영구 보존

**결론: "로그인 없음"과 "영구 기록"은 오너/참여자 역할을 나누면 둘 다 지킬 수 있다.**

- **충돌 지점**: "로그인 없음"=참여자 마찰 제거용. 이번 요청(영구 기록)=오너의 소유권·영속성 문제 → 다른 축
- **절충 해법**
  - 오너: Google/GitHub 로그인, 계정에 프로젝트 귀속
  - 참여자: 기존과 동일, 이름만 입력
- ✅ **확인 완료**: 참여자는 로그인 없이 링크 참여 유지. 리더가 프로젝트를 생성하고 링크를 공유하는 구조로 확정
- ✅ **구현 시점 확정 (v20)**: 로그인 기능은 **테스팅이 얼추 완료되는 시점**에 착수 예정. 지금은 의도적으로 미루는 것 — 6-1(리더/팀원 화면 분리), 수익화(무료 한도) 등 로그인에 종속된 항목들도 자연히 같은 시점 이후로 순연됨

### 6-1. 리더/팀원 권한 분리 (v26 — 2건 확정, 1건 남음)

로그인 착수와 함께 세부를 확정한다. UI 문구에 이미 "리더가" 라는 표현이 박혀 있던 항목(13-6)들을 실제 권한 체크로 승격하고, 그 외 항목은 이번에 새로 판단해 제안했다.

| 기능 | 권한 | 근거/상태 |
|---|---|---|
| 회의 녹음 시작/종료 | 참여자 누구나 | ✅ 기존 확정 (개인 선택 기능) |
| 회고 "완료" 처리 | 참여자 각자 자기 몫만 | ✅ 기존 확정 (5장) |
| STEP 안내 배너 편집 | **리더 전용** | ✅ 구현·검증 완료. UI 읽기전용 + DB 트리거로 이중 강제 |
| 1인당 투표권 수 조정 | **리더 전용** | ✅ 구현·검증 완료. 팀원에겐 숫자만 노출, 조정 UI 자체 없음 + DB 트리거 이중 강제 |
| 프로젝트 삭제 | **리더 전용** | ✅ **확정 (3차 명세서로 확인).** RLS+UI 양쪽 강제 구현됨 |
| 문제 정리 탭 문구 다듬기 | **참여자 누구나** | ✅ **확정 (3차 명세서로 확인).** 제안대로 구현됨 |
| 문서 표준 4필드 편집(목적/배경/추진방향/기대효과) | 참여자 누구나 (제안) | ⚠️ **여전히 미확인.** 3차 명세서 8장(문서)에 권한 열이 없어 확인 안 됨 — 다음 라운드에 확인 필요 |
| 포스트잇 작성/병합/문제표시/보류, 투표 참여, 프로젝트 목표 편집 | 참여자 누구나 (변경 없음) | 기존 그대로, 구현 확인됨 |
| docx/마크다운 다운로드, 이미지 저장, 프롬프트 추출 | 참여자 누구나 (변경 없음) | 읽기·내보내기 성격, 구현 확인됨 |

**권한 이중 강제 원칙 확인됨**: UI 숨김만으론 API 직접 호출 우회가 가능해서, 오너 전용 기능은 RLS 또는 트리거로도 항상 막는다는 원칙이 실제로 지켜지고 있음(명세서 "설계 원칙 메모" 확인) — 특히 `projects` 테이블의 `instructions`/`votes_per_user`는 RLS가 행 단위라 컬럼별 보호가 안 돼서, 트리거로 컬럼 단위 오너 검사를 추가한 것으로 확인됨.

**기술적 전제**: OAuth는 실제 도메인·백엔드·DB 필요 → Claude 아티팩트 환경 불가능 → **프로토타입에서 실배포 앱으로 전환 신호**

**구현 옵션 (난이도 낮은 순)**: Supabase Auth(DB 포함) > Clerk(UI 완제품, DB 별도) > Auth.js(자유도 높음, 조립 많음)

**수익화 (확정)**
- 계정당 무료 프로젝트 개수 제한(예: 2개) → 초과 시 구독/건당 결제
- DB 설계 시부터 "사용자-프로젝트" 1:N이 아니라 사용자에 plan·사용량 필드 포함
- 정확한 숫자·가격은 보류 (데이터 없이는 추측) — 지금은 "구조만" 준비, Stripe 연동은 이후 결정

### 7-1. PRD 4요소 보강 (Must 한정, 강의 개념 적용)

## 9. 리스크 및 추가 조사 필요 사항

**결론: 가장 큰 리스크는 "범위 확장"과 "간격 문제" — 둘 다 지금 구조의 근본 가정과 직결된다.**

- **동시편집 한계**: 2초 폴링, 10명↑ 동시 작업 시 지연·충돌 가능 — 실사용 규모 확정 필요

- **범위 확장 리스크**: 아이데이션+회고 통합 = "한 곳에서 다 됨" 장점 + "둘 다 어중간" 위험 공존
- **간격 문제**: 분기 단위 프로젝트는 팀 재방문 확률↓, 스프린트 단위(1~2주)는 연결이 자연스러움 → 목표 사용자 재조정 가능성

| 지표 | 수치 | 출처 |
|---|---|---|
| 연간 회의 시간 | 평균 392시간/년 | Fellow, 2025 |
| 비생산적 인식 | 67% | Fellow, 2025 |
| 집중력 손실 | 30분 내 52% | Flowtrace, 2025 |

### 10-2. "동시에 쓰기"의 학술적 근거

| 연구 | 핵심 | 연결 |
|---|---|---|
| Production Blocking (Diehl&Stroebe, 1987/91) | 발언 순서 대기 구조가 생산성 저하 유발 실증 | 동시 작성 설계의 이론적 근거 |
| 메타분석 (Mullen et al., 1991) | 개인 작업이 그룹 대비 평균 83% 더 많은 아이디어 | 정량적 근거 |
| NGT (Delbecq&Van de Ven, 1975~) | 침묵 작성→공유→명확화→투표 구조가 동조 감소 | 현재 워크플로우와 구조적 동일 |

### 10-3. NGT 장단점

| 구분 | 내용 |
|---|---|
| 장점 | 동등 참여 보장, 시간 절약, 아이디어量 증가, 종결감 제공 |
| 단점 | 한 번에 한 주제만(→다중 보드로 대응 중) |
| 단점 | 숙련 퍼실리테이터·준비시간 필요(→온라인 경량화로 상당수 해소 주장 가능) |
| 단점 | 초기 침묵 단계 즉흥성 제한(→병합이 보완하는지 검증 필요) |

### 10-4. 문서 반영 요약

| 대상 | 반영 내용 |
|---|---|
| 1장 | 캠프 관찰(1차) + production blocking(보조) |
| 가설 F | 핵심 효과는 병합보다 "동시 작성" 단계 — 검증 우선순위 조정 |
| 4장 | "숙련 퍼실리테이터 불필요" 포지셔닝 근거 |
| 7장 | 다중 보드 = NGT 약점 선제 대응 |

## 11. 학술적 근거에 대한 반론과 한계

**결론: 반박 가능한 지점이 최소 2곳(11-1, 11-3) 있고, 1곳(11-2)은 업계 관행 자체의 약점이다. 숨기지 않는다.**

### 11-1. Production Blocking은 EBS에서 다른 이야기

- Diehl&Stroebe(1987)는 **대면 회의** 전제 — 타이핑 방식은 "전자 브레인스토밍(EBS)" 별도 범주
- Dennis&Valacich(1993): EBS는 production blocking 사실상 없음 (유리)
- **BUT** Dennis&Valacich(1999): EBS 우위는 9명↑ 큰 그룹부터. 5~8명은 개인작업과 차이 없거나 미결론
- **BUT** Pinsonneault et al.(1999): EBS 우위 자체가 "착시(illusion)"일 수 있다는 반박, 논쟁 진행 중

→ **함의**: 목표 사용자(5~15명) 중 5~8명 구간은 학계 미결론 영역. **가설 F는 "5~8명에서는 성립 안 할 수도 있다" 전제로 재작성 필요**

### 11-2. 회고 자체의 실증 근거가 얇음

- 회고는 압박 시 가장 먼저 부실화/생략되는 관행으로 반복 보고
- 게임형 회고 개선 시도의 효과 근거는 거의 없음
- 학생 팀 실증 연구: 성찰 수준이 피상적

→ **함의**: 4장 차별점 5번이 "학계도 증명 못한 가정" 위에 있음. "회고를 더 잘하게"보다 "회고를 하긴 하게"(완료 전환율)에 먼저 집중이 현실적

### 11-3. 실명 공개 투표의 편향 위험 — 검토 후 실명 유지로 최종 확정 (v20)

- 닷보팅: 명시 기준 없어 편향·위계·지배적 목소리에 왜곡 가능
- 공개 투표: 다수/영향력자 쏠림 위험, 익명 투표 권고 다수

**반론(타당함)**: "이름 알아야 발언 가능한 거 아니냐" → 맞음. 완전 익명은 1장 핵심 기능(되묻기) 자체를 무너뜨림

**✅ 최종 결정 (v20)**: 절충안(진행 중 익명·종료 후 공개) 대신, **투표도 의견과 마찬가지로 상시 실명 공개로 확정**한다. 이유는 "누가 왜 투표했는지 궁금할 수 있다"는 것 — 1장부터 일관되게 써온 원칙(이름이 있어야 되물을 수 있다)을 투표에도 그대로 확장한 결정이다.

**인지하고 가는 트레이드오프**: 위에서 인용한 문헌대로, 실명 공개 투표는 다수 의견·영향력 있는 구성원 쪽으로 쏠리는 편향을 만들 수 있다는 지적이 실제로 있다. 이 프로젝트는 "편향 감소"보다 "사후 논의 가능성"을 우선순위로 택한 것이며, 이건 근거가 없어서가 아니라 **알면서 택한 트레이드오프**다. 가설 I는 별도 실험 대상에서 제외하고, "실명 투표에서 쏠림 현상이 실제로 얼마나 발생하는지"는 8장 지표(득표 분포 등)로 사후 관찰하는 정도로 남긴다.

### 11-4. 확실한 것 vs 불확실한 것

| 가정 | 확실성 |
|---|---|
| 대면 발언 순서 대기 → 생산성 저하 | 확실 (40년 검증) — 단, 우리는 디지털이라 그대로 적용 안 됨 |
| 디지털 동시작성, 5~8명에서도 효과 | **불확실** (11-1) |
| NGT 구조가 동등 참여 보장 | 비교적 확실 (단점 존재) |
| 회고가 팀에 도움 | **생각보다 약함** (11-2) |
| 실명 투표가 공정한 결과 | **반대 증거 있음 — 알면서 실명 유지로 확정 (11-3, v20)** |

## 13. 배포 현황 및 서비스명

**결론: 저장 방식·"문서" 탭 정체는 확인 완료. 대신 계획-실구현 사이 불일치 2건과 미구현 1건을 새로 발견했다.**

- **서비스명**: Onalign, 배포 화면 타이틀·메타설명에도 반영 확인
- **배포**: https://onalign.vercel.app — 6장 "프로토타입→실앱 전환" 진행 중

### 13-1. 지난 라운드 미확인 사항 → 확인 완료

| 항목 | 확인 결과 |
|---|---|
| 데이터 저장 방식 | 이원화 확인: 참여자 이름 재진입 기억=localStorage(클라이언트), 프로젝트/보드 데이터=Supabase(서버) |
| "문서" 탭의 정체 | 5장 회고(KPT) 화면이 **아님**. 과정 문서/결과 문서(TOP5)를 HTML·마크다운·이미지로 내보내는 리포트 화면으로 확인됨 |

### 13-2. 계획-구현 불일치 → 최종 확정 (2차 명세서로 재확인)

| 항목 | 상태 |
|---|---|
| 우선순위 투표 위치 | ✅ **"우선순위 결과" 탭에서 투표하는 것으로 최종 확정.** 2차 명세서에서도 동일하게 재확인되어, 의도적 설계로 받아들이고 5·7장 서술을 이 기준으로 정리한다 |
| 투표 익명 절충안(11-3, 가설 I) | ✅ **결정 완료 (v20).** 절충안을 기각하고 상시 실명 공개로 확정 — 이유는 "누가 왜 투표했는지 궁금할 수 있다"는 것, 1장 되묻기 원칙의 연장선. 편향 위험은 인지한 채로 감수하는 트레이드오프로 명문화(11-3 참고) |

### 13-3. 5장(아이데이션→회고 연결) — 구현 완료 확인

2차 명세서(6. 회고)로 v18 설계와 전부 대조 확인됐다: 참여자별 KPT(본인 칸만 편집), 개인 단위 "완료"(완료 안 한 회고는 문서 미반영, 완료 후에도 수정 가능하고 수정 즉시 문서 반영), 우선순위 해결여부 토글(기본 켜짐) — **설계와 구현이 정확히 일치.** 남은 열린 질문 없음.

### 13-4. 음성 녹음 기능 — 계획보다 가볍고, 더 완성도 있게 구현됨

계획(15장 3번)은 Whisper 등 외부 STT + 서버리스 함수를 전제했는데, 실제로는 **브라우저 내장 Web Speech API**로 구현됐다. 2차 명세서로 세부가 더 확인돼 아래처럼 갱신한다.

- 서버·외부 API 비용 없음 → **"유료 플랜 전용 기능" 후보였던 수익화 근거는 소멸** (6장 참고)

**🚨 최우선 사항**: 0장 요약 참고 — 팀원 익명 참여가 폐지되고 전원 구글 로그인 필수로 바뀜. 의도한 방향인지 확인 필요.

**⚠️ 배포 상태 경고 (중요)**: 명세서 원문에 명시된 대로, 아래 항목들은 **로컬 코드는 완성됐지만 배포(git push)와 실사용자 계정 검증이 아직 안 된 상태**다 — 구글 로그인, 팀원 로그인 필수화, 공유 링크(`?p=id`), 리더 권한 분리, 헤더 배지 통합. 이 문서에서도 이 항목들은 "구현 완료"가 아니라 "로컬 완성, 배포 검증 대기"로 별도 표기한다(0장 참고). Supabase schema.sql은 이미 1회 실행되어 로그인·프로젝트 생성까지는 사용자가 직접 확인함.

**6-1 권한 매트릭스 갱신**: 프로젝트 삭제(리더 전용)와 문제 정리 문구 편집(참여자 누구나) 확정 확인됨. 문서 표준 4필드 편집 권한만 아직 미확인 상태로 남음.

**5-4 정렬 기준 확정**: 정렬 통일 버그 수정 확인됨. 다만 "우선순위 결과" 탭의 동점자 2차 정렬(빠른 표시순)이 "문제 정리" 탭(최근 표시순)과 **의도적으로 반대 방향**이라는 게 명세서에 명시됨 — 왜 두 탭을 다른 방향으로 뒀는지 구체적 근거는 명세서에 없어, 필요하면 다음에 확인.

**5-2 녹음-문서 연동**: 과거 지적했던 경합(race condition) 버그 수정 확인됨.

**데이터 아키텍처 변경 확인**: `projects`가 예전엔 kv_store 안 JSON 배열이었는데, 오너 단위 행 권한 적용을 위해 **진짜 테이블로 이관**됨. RLS는 행 단위 제어만 가능해 컬럼별 보호(예: `instructions`, `votes_per_user`만 오너 제한)가 안 되는 한계를, 트리거로 보완한 것으로 확인 — 이건 이 프로젝트 전체에서 가장 기술적으로 정교한 설계 결정 중 하나로 기록해둘 만함.

**그 외 신규 확인**: 포스트잇을 빈 공간 클릭만으로도 생성 가능(버튼 클릭 없이), 헤더의 이름·색깔점 배지가 중복 없이 하나로 통합됨.

| 확정/논의중 미구분 | 최종안 못 찾음, 중복 논의 발생 | "문제로 상단고정" 기능이 정확히 겨냥 — 설계 방향 실증 |
| 목표 미합의 진행 | 결과물 완성 후 서로 다른 정의였음을 인지. 한 팀은 "align" 단어 직접 사용 | 1장 핵심 재정의 실증, 서비스명과 우연 일치 |
| 인원↑ 동기화비용↑ | 6인 팀, 조율에 매일 추가시간 소요, 피로 누적 | 가설 H(5~8인 효과)에 대한 실제 사례 1건 (표본1, 방향성 지지) |
| 주제 이탈 | 논의 중 이탈로 회의 장기화 | 4장 차별점 1번과 정확히 일치 |

> **한계**: 무작위 표본 아님(같은 캠프), 12장 설문과 유사 편향. 단, Onalign 존재 전 작성된 회고라 확증편향보다 "우연한 실증"에 가까움

## 15. 이번 근거로 추가 제안하는 기능 (검토 필요)

**결론: 신규 기능 3개 제안 — 확정 아님, 검토 요청.**

1. **보류함(파킹랏)**: "나중에" 태그로 미결 안건 별도 보관 — "미결 기록 누락" 대응
2. **프로젝트 목표 한 줄 고정**: 프로젝트 생성 시 목표 한 줄 입력→상단 고정 — "목표 미합의" 대응
3. **회의 녹음 → 텍스트 변환** — **구현 완료 (13-4 확인)**: 참여자 누구나 개인 선택으로 녹음 시작/종료. 계획 당시 Whisper 등 외부 STT + 서버리스 함수를 전제했으나, 실제로는 **브라우저 내장 Web Speech API**로 구현되어 실시간 자막 패널(임시 텍스트 회색 표시), 중복 문장·단어 정리, `.txt` 다운로드까지 포함됨. 녹음 중지 시 결과는 **문서 탭 "회의 녹취록"에 직접 반영** (최초 계획했던 "포스트잇으로 저장"이 아니라 5-2장 목적대로 문서 보강으로 최종 확정)
   - **목적 재확인**: 발화자 구분이 아니라 "문서 탭 요약 문구가 어떤 맥락에서 나왔는지" 되짚을 원본 자료 확보 — 1장 핵심 문제(의도 파악 실패)를 보강하는 방향으로 판단
   - **권한**: 프로젝트 참여자 누구나 시작 가능 (리더 전용 아님) — 확정됨
   - **비용 구조 (수정)**: 서버·외부 API 없이 브라우저에서 완결 → 비용 없음. **"유료 플랜 전용 기능" 후보였던 수익화 근거는 소멸** — 6장 수익화 논의에서 이 항목 제외
   - **새로 생긴 제약**: Chrome/Edge 한정 (Web Speech API 브라우저 지원 범위), 브라우저가 인식을 자동 종료시킬 때 재시작 로직 필요 — 권한 거부·미지원 브라우저 예외 처리는 이미 구현됨(17장 정책과 일치)

→ 셋 다 7장 MVP 표에 반영 완료 (1, 2번은 Should 대기, 3번은 구현 완료)

## 16. 로그 설계 (강의 개념 + 필자 판단)

**결론: 8장 지표를 계산할 원본 로그가 없었다. 최소 5개 이벤트로 깔때기 구성 가능하다.**

> 출처 구분: pageview/event 구분 프레임워크 = 강의 개념. 아래 구체 스키마 = 필자 적용

| 종류 | 이벤트명 | 속성 | 대응 지표 |
|---|---|---|---|
| pageview | `tab_view` | project_id, tab_name, timestamp | 세션 완료율 |
| event | `note_created` | project_id, note_id, user_name, timestamp | 평균 포스트잇 수 |
| event | `note_promoted_to_problem` | project_id, note_id, timestamp | 문제정리 도달 여부 |
| event | `vote_cast` | project_id, note_id, user_name, timestamp | 투표 참여율 |
| event | `project_status_changed` | project_id, from_status, to_status, timestamp | 완료 전환율 |

→ "의견작성→문제등록→투표→완료" 깔때기 구성 가능. 실구현 시 이벤트명·속성 변경 가능성 있음

## 17. 에러케이스 / 정책 (강의 개념 + 필자 판단)

**결론: 정책 섹션 자체가 없었다. 최소 4개 케이스를 제안한다 — 확정 아님.**

> 출처 구분: "실패 케이스를 정책으로 정의" 프레임워크 = 강의 개념. 개별 케이스·정책 = 필자 판단

| 케이스 | 문제 소지 | 제안 정책 |
|---|---|---|
| 투표권 동시 소진 충돌 | 2초 폴링 구조상 동시 사용 시 유실/초과 가능 | 저장 시점 서버 잔여 재확인, 초과 시 후순위 요청 거부+알림 |
| 저장 실패(네트워크) | Supabase 저장 실패 시 입력 유실 가능 | 재시도 안내 + 로컬 임시보관 후 재전송 |
| 오너 계정 이탈 | 오너 삭제/이탈 시 참여자 접근권 불분명 | 오너 삭제 시 프로젝트 읽기 전용 전환 |
| 동명이인 충돌 | 같은 이름 2인 참여 시 구분 불가 | 재입력 시 자동 구분자 부여(지연, 지연_2) |
| 녹음 중 미인지 (신규, 15장 3번 연결) | 누군가 녹음을 시작해도 다른 참여자가 모를 수 있음 — 개인 선택 기능이라도 진행 중임은 전원이 알아야 함 | 녹음 중에는 상단에 "🔴 녹음 중" 배지를 모든 참여자 화면에 상시 노출 |

## 18. 데이터 드리븐 기획 5단계 검토 (강의 개념)

**결론: "문제 정의"는 두텁고 "지속 개선"은 가장 얇다.**

> 출처 구분: 5단계 프레임워크 = 강의 개념. 단계별 평가 = 필자 판단

| 단계 | 상태 | 이유 |
|---|---|---|
| 문제 정의 | 충분 | 관찰+이론+실사례 3중 근거 |
| 데이터 수집·분석 | 부분적 | 외부·자사 데이터는 완료, 1차 설문은 계획 단계 |
| 가설 수립·실험 | 가설 강함/실험 약함 | H·I 실험설계(표본·기간·기준) 뼈대만 존재 |
| 결과 분석·의사결정 | 기준만, 실행 전 | 데이터 미수집 — 진행단계상 당연한 공백 |
| 지속 개선 | 암묵적 존재만 | 재검토 주기 미명시 |

**지속 개선 재검토 시점 (신규)**
- 설문 응답 20건 이상 도달 시
- 실사용 배포 후 4주 경과 시
- Could 항목 실행 결정 시

## 19. 문서화·녹음·프롬프트 추출 고도화 제안 (v30, 무료 범위 내)

**결론: 셋 다 서버 비용·유료 API 없이 더 밀어붙일 여지가 있다. 우선순위 3단계로 나눈다.**

전제: 이 장의 모든 항목은 클라이언트 코드 또는 기존 무료 API(Web Speech API 등) 범위 안에서 구현 가능하다는 것을 확인하고 제안한 것들이다 — 유료 API·서버 비용이 필요한 항목은 의도적으로 제외했다.

### 19-1. 우선순위 1 (버그성, 우선 처리)

| 항목 | 내용 |
|---|---|
| 동시 녹음 충돌 방지 | 참여자 누구나 녹음 가능(기존 확정)은 유지하되, 이미 녹음 중일 때 다른 사람의 시작 버튼은 비활성화 |

### 19-2. 우선순위 2 (체감 효과 가장 큼)

| 항목 | 내용 |
|---|---|
| 프롬프트 템플릿 선택지 | "정리된 문서로" 외에 "액션 아이템만", "슬랙 공유용 짧은 요약", "경영진 보고용 formal 톤" 등 프리셋 2~4개 버튼 — 지시문 텍스트만 교체, 비용 없음 |
| 포함 항목 체크박스 | 프롬프트 추출 시 회의 녹취록·완료된 회고 등을 포함할지 선택 — 프롬프트가 너무 길어져 AI 채팅창에 못 붙여넣는 문제 완화 |

### 19-3. 우선순위 3 (여유 될 때)

| 항목 | 내용 |
|---|---|
| PDF 내보내기 | jsPDF 등 클라이언트 전용 라이브러리로 서버 비용 없이 추가 |
| 문서 스냅샷(버전 고정) | "이 시점으로 고정" 버튼 — 클라이언트에서 JSON 스냅샷 별도 저장. 예전 PM 역질문에서 물었던 "특정 시점 확정본을 남길 방법" 질문에 대한 답 |
| docx 서식 보강 | 목차(TOC), 생성일자 푸터 추가 |
| 녹음 언어 선택 | Web Speech API `lang` 파라미터 교체만으로 가능 |
| 일시정지 vs 완전 종료 구분 | 회의 중 짧은 중단은 이어서, 끝나면 문서 반영으로 명확히 분리 |
| 회의 녹취록 인라인 편집 | 오탈자·오인식 교정 가능하게 — 문서 표준 4필드와 동일한 편집 패턴 재사용 |
| 프롬프트 복사 전 미리보기 + 글자 수 표시 | 불필요한 부분 미리 제거 가능하게, 길이 제한 있는 AI 채팅창 대비 |
