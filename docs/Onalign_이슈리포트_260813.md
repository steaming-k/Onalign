# Onalign 실배포 사이트 이슈 리포트

**점검일** : 2026-08-13
**대상** : https://onalign.vercel.app (로그인 없이 접근 가능한 공개 영역)
**기준 문서** : Onalign 기능 명세서 v3 (2026-08-03), Onalign 기획서 v32 (이 리포트의 발견은 기획서 v33의 13-15장에 요약해 반영했다 — 두 문서를 쌍으로 읽는다)
**이 문서의 독자** : 본인 — 실행자 겸 의사결정자. 따라서 '무엇이 잘못됐는지'보다 **'무엇을 먼저 고칠지, 어떻게 다시 확인할지'**를 기준으로 정리했다.

## 0. 요약

### 핵심 발견 4가지

1. **초대 링크가 향하는 `app.html`에 메타 태그가 하나도 없다.** OG 태그를 이번 라운드에 새로 붙였지만 랜딩 페이지에만 들어갔다. 정작 메신저로 공유되는 URL은 미리보기 카드가 뜨지 않는다. 제품의 유입이 '링크 공유' 하나에 걸려 있다는 점에서 우선순위가 가장 높다.
2. **파비콘이 배포에 없다.** `/favicon.ico`와 `/favicon.png`가 모두 404이고, 조회한 세 페이지(`index.html`·`app.html`·`terms.html`) 모두에서 `rel=icon` 링크 태그가 검출되지 않았다(도구 기준 — 확정은 개발자도구로 한 번 더 봐야 한다). 명세서에는 '교체 완료'로 기록돼 있다 — 기획서 13-12에서 남긴 '로컬 완성 ≠ 배포 확인' 교훈이 같은 형태로 재발한 사례다.
3. **약관·방침이 배포되면서 '문서가 약속한 것'과 '제품이 할 수 있는 것'의 간극이 실제 리스크가 됐다.** 국외 이전 고지 누락(법정 항목)과 삭제 요청 이행 수단 부재 두 건이 확인된다.
4. **랜딩 카피의 4단계 잔재가 위치만 옮겨 남았다.** 히어로에서는 4단계 미리보기 칩이 검출되지 않았지만(해소된 것으로 추정), 차별점 카드 1번 본문은 여전히 '의견 → 병합 → 문제 정리 → 투표'다. 부수적으로 '병합'이 흐름 섹션에는 단계로 없고 카드에는 있어 **단계 명칭 체계가 두 갈래**다.

### 심각도 분포

| 심각도 | 건수 | 성격 |
|---|---|---|
| P1 (공개 확대 전 처리) | 4 | 유입 손실, 배포 누락, 법정 고지 항목 |
| P2 (다음 라운드) | 4 | 카피 정합성, 방침 표준 항목, 약관 공백 |
| P3 (여유 될 때) | 3 | OG 이미지 품질, 크롤러·404, 문의처 노출 |
| 점검 불가 | 6개 영역 | 도구 제약 — 6장에 자가 점검 체크리스트를 남겼다 |

### 점검 방법과 그 한계 (먼저 밝힌다)

| 구분 | 내용 |
|---|---|
| 확인한 것 | 각 페이지 본문 텍스트, `<head>`의 메타·링크 태그, 정적 리소스 응답 코드(200/404), 없는 경로의 응답 코드, 약관·방침 조문 내용 |
| 확인하지 못한 것 | ① 반응형 3구간 렌더링 ② 5단계 카드 높이 통일 ③ 브라우저 콘솔 오류 ④ 로그인 게이트 이후 모든 화면 ⑤ 존재하지 않는 `?p=` 처리 화면 ⑥ 404 화면의 실제 모습 |
| 이유 | 이 세션 환경에서 브라우저 직접 접속이 차단돼 있고, 브라우저 확장도 연결되지 않았다. 텍스트·메타 레벨만 조회 가능한 방식으로 점검했다 |
| 그래서 | 렌더 레벨 항목은 **'문제 없음'이 아니라 '확인 안 됨'**이다. 6장에 직접 확인할 체크리스트를 남긴다 |

## 1. P1 — 공개 확대 전에 처리

### P1-1. 공유 링크(`app.html`)에 OG·description·canonical·favicon 링크가 전부 없다

| 항목 | 내용 |
|---|---|
| **확인된 사실** | `app.html`의 `<head>`에는 `viewport` 메타 1개와 `<title>Onalign — 퍼실리테이션 보드</title>`만 있다. `description`, `og:*`, `twitter:*`, `canonical`, `rel=icon` 전부 없음. 반면 `index.html`에는 OG·Twitter·canonical·description이 모두 정상 존재한다 |
| **왜 문제인가** | 제품의 참여 흐름은 '오너가 프로젝트를 만들고 링크를 공유 → 팀원이 링크로 진입 → 구글 로그인'이다. **가정 (확인 필요)** : 실제로 메신저에 붙는 URL이 랜딩이 아니라 앱 URL(`app.html?p=...`)이라는 전제 위에 있다. 랜딩 CTA가 `/app.html`로 향하는 것은 확인했으나, 오너가 복사하는 공유 링크의 정확한 형태는 로그인 없이는 확인하지 못했다 — **이 전제가 틀리면 이 이슈의 우선순위는 내려간다. 링크 하나 복사해서 형태를 보는 것이 이 리포트에서 가장 먼저 할 확인이다.** 전제가 맞다면, 카카오톡·슬랙은 OG 태그로 미리보기를 만들기 때문에 지금 상태에서는 설명도 이미지도 없이 `<title>`만 노출되거나(플랫폼별 폴백 차이) 미리보기 자체가 생기지 않는다 |
| **추정 (검증 필요)** | 미리보기가 없는 링크는 클릭률이 낮아질 수 있다. 이건 가설이며, 기획서 12장 가설 A를 재작성할 때 '구글 로그인 마찰'과 '링크 신뢰도'를 분리해서 물어야 확인된다 |
| **원인 가설** | 이번 라운드의 OG 작업이 '랜딩페이지 개편' 항목 안에서 진행됐다. 랜딩(`index.html`)은 손으로 쓴 정적 파일이고 앱은 Vite 엔트리라 파일이 갈라져 있어, 랜딩 작업 범위에 앱 엔트리가 포함되지 않은 것으로 보인다 |
| **제안 조치** | ① `app.html`에 OG·Twitter·description·canonical 세트를 넣는다. 프로젝트별 동적 값은 정적 호스팅에서 불가하므로 **프로젝트 이름이 아니라 서비스 단위 기본값**으로 넣는다(예 : `og:title` = 'Onalign 프로젝트에 초대되었습니다', `og:description` = '링크로 들어가 구글 계정으로 로그인하면 바로 참여됩니다') ② 초대받는 사람이 볼 문구라는 점을 감안해 랜딩 카피를 그대로 복사하지 말고 초대 상황에 맞게 쓴다 |
| **재확인 방법** | 실제 링크를 카카오톡 '나에게 보내기'와 슬랙 DM에 붙여 미리보기를 확인한다. 캐시 때문에 즉시 반영되지 않으므로 쿼리스트링을 바꿔 재시도하거나 각 플랫폼 디버거를 사용한다 |

> **판단** : 이 항목이 P1인 이유는 기술적 심각도가 아니라 **깨진 것이 하필 유일한 유입 경로**라는 데 있다. 기획서 4장 차별점 1번이 v28에서 '전원 구글 로그인, 링크 하나로 즉시 합류'로 재정의됐는데, 그 링크가 미리보기 없는 상태로 공유되고 있을 가능성이 있다.

### P1-2. 파비콘이 실배포에 없다

| 항목 | 내용 |
|---|---|
| **확인된 사실** | `/favicon.ico` → 404, `/favicon.png` → 404. 대조군으로 확인한 `/onalign-logo.png`는 정상 응답(200) |
| **확인된 사실 2** | 조회한 세 페이지(`index.html`, `app.html`, `terms.html`) 어디에도 `rel=icon` 링크 태그가 검출되지 않았다(`apple-touch-icon` 부재는 `index.html`에서만 확인했다). 같은 조회에서 `canonical` 링크 태그는 정상 검출됐으므로, **링크 태그를 못 읽는 문제는 아니다** |
| **결론과 신뢰도** | 응답 코드 404는 사실이다. 링크 태그 부재는 조회 도구 기준이라 **높은 확률의 추정**으로 둔다. 다만 두 결과를 합치면 결론은 같다 — 브라우저는 링크 태그가 없으면 `/favicon.ico`로 폴백하는데 그것도 404이므로, **탭 아이콘은 표시되지 않는다** |
| **명세서와의 불일치** | 기능 명세서 v3은 '파비콘(로고 심볼만 정사각 크롭, 468x155 워드마크를 그대로 쓰던 것에서 교체)'을 완료 항목으로 기록했다. 실배포에는 없다 |
| **원인 가설** | 명세서 자체에 같은 유형의 주의가 이미 적혀 있다 — '`vite.config.js`의 빌드 입력에 반드시 등록해야 배포에 포함됨(안 하면 404)'. 파비콘 파일이 `public/`에 들어가지 않았거나, 링크 태그만 쓰고 파일 배치를 빼먹은 경우로 추정 |
| **제안 조치** | ① `public/favicon.ico`(또는 `favicon.png` 32x32·180x180)를 배치한다 ② 세 HTML 모두에 `rel=icon`을 명시한다 — 앱 엔트리는 Vite가 처리하므로 따로 확인한다 ③ 커밋 후 배포된 URL로 응답 코드를 직접 확인한다 |
| **재확인 방법** | 배포 사이트에서 개발자도구 → Elements로 `<head>` 확인, Network 탭에서 favicon 요청의 상태 코드 확인. 하드 리프레시 필요(파비콘은 캐시가 강하다) |

> **판단** : 이 건은 단독으로는 사소하다. 문제는 **13-12에서 '로컬 완성 ≠ 배포 확인'을 교훈으로 명문화한 직후 라운드에 같은 형태가 또 나왔다**는 점이다. 교훈을 문서에 적는 방식으로는 재발이 막히지 않았으므로, 배포 후 확인 항목을 4개로 고정하는 편이 낫다 — 랜딩 렌더 / 파비콘 / 공유 링크 미리보기 / 약관·방침 200 응답.

### P1-3. 개인정보처리방침에 국외 이전 고지 항목이 없다

| 항목 | 내용 |
|---|---|
| **확인된 사실** | 위탁 표에 `Supabase — 데이터베이스 저장 및 관리 — 해외 서버에 저장될 수 있음`, `Vercel — 웹사이트 호스팅 — 해외 서버에 저장될 수 있음`으로만 기재돼 있다. '개인정보 국외 이전'이라는 별도 항목과 그 법정 기재사항이 없다 |
| **왜 문제인가** | 개인정보 보호법은 개인정보를 국외로 이전하는 경우 ① 이전받는 자 ② 이전되는 항목 ③ 이전 국가·시기·방법 ④ 이전 목적 ⑤ 보유·이용 기간 ⑥ 거부 방법과 절차를 알리도록 한다(제28조의8). '해외 서버에 저장될 수 있음'은 이 항목들을 대체하지 않는다. 또한 처리방침 필수 기재사항은 제30조에 열거돼 있다 |
| **추가 고려** | Supabase·Vercel은 위탁이자 국외 이전에 해당하므로, 위탁 표와 국외 이전 표를 **분리해서** 쓰는 편이 명확하다. 리전을 확인해 국가를 특정할 수 있으면 특정한다(Supabase 프로젝트 리전은 대시보드에서 확인 가능) |
| **제안 조치** | 방침에 '개인정보의 국외 이전' 항목 신설 + 위 6개 기재사항 표. 거부 방법은 현실적으로 '서비스 이용 중단'이 되므로 그대로 쓴다 |
| **왜 P1인가** | 법정 고지 항목이라는 점, 그리고 구글 OAuth 앱을 테스트 범위 밖으로 공개할 때 개인정보처리방침이 검수 대상이 된다는 점 때문이다. 개인 프로젝트라는 이유로 넘길 수 있는 항목이 아니다 |
| **출처** | 개인정보 보호법 : https://www.law.go.kr/법령/개인정보보호법 · 개인정보보호위원회 : https://www.pipc.go.kr · Google API Services User Data Policy : https://developers.google.com/terms/api-services-user-data-policy |

### P1-4. 방침이 약속한 권리를 이행할 수단이 제품에 없다

| 항목 | 내용 |
|---|---|
| **확인된 사실 (방침)** | 보유·이용 기간 = '이용자가 계정을 삭제하거나 프로젝트를 삭제할 때까지'. 이용자의 권리 = '열람·정정·삭제 요청', '프로젝트 삭제를 통한 콘텐츠 전체 삭제', '로그아웃 및 재로그인을 통한 이용 중단'. 행사 방법 = 문의처 이메일로 요청 |
| **확인된 사실 (제품, 명세서 기준)** | 기능 명세서 v3에 **계정 삭제(탈퇴) 기능이 없다.** 프로젝트 삭제는 오너 전용이다 |
| **간극 3가지** | ① 보유기간의 기준점으로 쓴 '계정 삭제'라는 상태가 제품에 존재하지 않는다 ② 오너가 아닌 참여자는 자기가 쓴 포스트잇·투표·회고를 스스로 지울 수단이 없다(개별 포스트잇 삭제는 가능하나 '내 데이터 전체 삭제'는 아니다) ③ 이메일 요청을 받으면 Supabase에서 직접 지워야 하는데, 그 절차가 어디에도 정의돼 있지 않다 |
| **제안 조치** | **단기(문서 쪽으로 맞춘다)** : 보유기간 문구를 실제 가능한 범위로 수정하고, 삭제 요청 처리 절차(어떤 테이블·어떤 키를 지우는지, `kv_store` JSON 안의 작성자 이름까지 포함하는지)를 개인 메모로 남긴다. **중기(제품 쪽으로 맞춘다)** : 계정 삭제 기능. 이때 '내가 쓴 포스트잇이 남의 프로젝트에 있는 경우'를 어떻게 처리할지가 실제 설계 쟁점이다(작성자 표기만 익명화 vs 콘텐츠 삭제) |
| **판단** | 지금 결정할 것은 기능을 만들지 여부가 아니라 **어느 쪽을 먼저 맞출지**다. 문서를 줄이는 쪽이 비용이 훨씬 낮고, 실사용자가 캠프 팀 규모인 현 단계에서는 그게 합리적으로 보인다 |

## 2. P2 — 다음 라운드

### P2-1. 차별점 카드 1번이 아직 4단계 (단계 명칭 체계가 두 갈래)

- **확인된 사실** : 차별점 카드 1번 본문 = '의견 → 병합 → 문제 정리 → 투표. 정해진 단계를 따라가면 결론까지 자연스럽게 도착합니다.' 같은 페이지의 흐름 섹션 = '의견 작성 → 문제 정리 → 우선순위 투표 → 회고 → 문서화'
- **두 가지 불일치** : ① 카드는 4단계, 흐름은 5단계(회고·문서화 누락) ② **'병합'이 흐름 섹션에는 단계로 없고 카드에는 있다**
- **왜 문제인가** : 랜딩의 역할은 '이 도구가 무슨 순서로 진행되는지' 한 번에 전달하는 것이다. 같은 화면에서 두 개의 순서가 보이면 그 역할이 깨진다. ②는 카피 오류가 아니라 **정의가 안 정해진 문제**다 — 병합은 독립 단계인지, 문제 정리 안쪽 동작인지
- **제안 조치** : 먼저 정의를 정한다. **제안은 '병합은 의견 작성 단계 안쪽의 동작'이다** — 명세서 기준 병합은 별도 탭이 아니라 의견 작성 탭 안의 모드이므로, 랜딩의 5단계 이름과도 이 정의가 가장 잘 맞는다. 그다음 카드 본문을 5단계로 통일한다. (기획서 5장 1번에는 병합이 독립 탭으로 적혀 있어 그 서술도 함께 고쳐야 한다)
- **참고** : 기획서 13-13 #1과 같은 뿌리다. 히어로에서는 검출되지 않았으나 카드에 남았다

### P2-2. 개인정보처리방침 표준 필수 항목 5개 누락

- **확인된 사실** : 현재 항목은 수집 항목 / 수집·이용 목적 / 보유·이용 기간 / 제3자 제공 / 처리 위탁 / 쿠키·로컬 저장소 / 이용자의 권리 / 문의처 / 방침 변경 (시행일 2026년 8월 3일)
- **누락 항목** : ① 개인정보의 파기 절차 및 방법 ② 개인정보의 안전성 확보 조치 ③ 권익침해 구제방법(개인정보 분쟁조정위원회·개인정보침해신고센터 연락처) ④ 개인정보 보호책임자의 성명 또는 직책(현재 이메일만) ⑤ 만 14세 미만 아동의 개인정보 처리 방침
- **왜 문제인가** : 개인정보 보호법 제30조 제1항이 처리방침에 포함할 사항을 열거하고 있다. ⑤는 서비스 성격상 대상이 아니라면 '만 14세 미만 아동을 대상으로 하지 않는다'고 적는 것으로 충족된다
- **제안 조치** : 항목 5개를 추가한다. ②는 실제로 하고 있는 것만 쓴다(예 : 전송 구간 HTTPS 암호화, Supabase RLS 기반 접근 제어, 접근 권한 최소화) — **하지 않는 조치를 쓰는 것이 안 쓰는 것보다 나쁘다**
- **출처** : https://www.law.go.kr/법령/개인정보보호법 · https://www.privacy.go.kr

### P2-3. 이용약관에 준거법·관할, 계약 해지, 유료 전환 대비 조항이 없다

- **확인된 사실** : 제9조(분쟁 해결)는 '상호 협의하여 해결하도록 노력한다'만 규정한다. 준거법·관할 법원 조항 없음. 회원 탈퇴·계약 해지 조항 없음. 제8조(면책)는 '현재 무료로 제공되며'를 전제로 한다. 시행일 2026년 8월 3일
- **왜 문제인가** : ① 협의 실패 시 절차가 없다 → 준거법(대한민국 법)과 관할(민사소송법에 따른 관할 또는 합의 관할) 한 줄이면 해소된다 ② 기획서 6장의 수익화(무료 프로젝트 개수 제한 → 초과 시 결제)를 실행하는 순간 유료 조항·결제·환불·청약철회가 필요해진다. 전자상거래법 적용 대상이 되기 때문이다
- **제안 조치** : 지금은 준거법·관할과 해지(탈퇴) 조항만 추가한다. 유료 조항은 **수익화 착수 조건에 '약관 개정'을 항목으로 넣어두는 것**으로 충분하다 — 지금 쓰면 추측으로 쓰게 된다
- **출처** : 전자상거래법 : https://www.law.go.kr/법령/전자상거래등에서의소비자보호에관한법률

### P2-4. 약관 제7조가 사용자에게 넘긴 책임을 제품이 돕지 않는다

- **확인된 사실 (약관)** : 제7조 — 녹음은 이용자의 자발적 선택이며, 운영자는 다른 참여자에게 녹음 표시를 제공하되 **참여자 전원의 동의 확보 책임은 녹음을 시작한 이용자에게 있다**. 음성은 브라우저에서 텍스트로 변환되고 서버로 전송되지 않으며 변환된 텍스트만 저장된다
- **확인된 사실 (제품 — 기능 명세서 v3 기준, 화면 확인은 못 했다)** : 녹음 중 배지 노출과 동시 녹음 방지는 명세서에 있다. **시작 시점의 동의 확인 절차는 명세서에 없다** — 실제 화면에 있는지는 로그인 후 확인이 필요하다
- **왜 문제인가** : 배지는 '지금 녹음 중임을 알리는' 장치이고, 약관이 요구하는 것은 '시작 전에 동의를 받는' 행위다. 둘은 다른 문제다. 책임을 사용자에게 넘긴 약관은 **제품이 그 책임을 이행할 수단을 제공할 때 설득력이 생긴다**
- **제안 조치** : 녹음 시작 버튼에 1회 확인 모달('참여자 전원에게 녹음 사실을 알렸습니까?') + 짧은 안내. 클라이언트 구현이라 비용이 없다. 기획서 17-2장 정책 표에 추가했다
- **부수 확인 필요** : 약관은 '음성이 서버로 전송되지 않는다'고 명시한다. Web Speech API는 브라우저 구현에 따라 **음성을 브라우저 벤더 서버로 보내 인식하는 경우가 있다**(크롬이 대표적이다). '우리 서버로 보내지 않는다'는 사실이지만 '어디로도 전송되지 않는다'로 읽히면 부정확하다 → 문구를 '운영자 서버로 전송하지 않으며, 음성 인식은 브라우저 기능을 사용합니다'로 정밀화하는 것을 제안한다

## 4. 기능 명세서 v3 기록 vs 실배포 대조

명세서에는 '로컬이 origin/main보다 13커밋 앞선 상태, git push는 사용자가 직접 진행'으로 기록돼 있었다. **실제로는 push가 이루어졌고, 랜딩·약관·방침 계열은 배포에 반영돼 있다.** 파비콘만 어긋난다.

|---|---|

## 6. 점검하지 못한 영역 — 직접 확인할 체크리스트

이 항목들은 **'문제 없음'이 아니라 '확인 안 됨'**이다. 브라우저에서 직접 확인하는 것이 가장 빠르다.

### 6-1. 렌더링 (브라우저 창 너비를 줄여가며 확인)

- [ ] 데스크톱(≥1060px) : 5단계 흐름도가 한 줄로 놓이는가
- [ ] 태블릿(641~1060px) : 3+2 그리드, 화살표 숨김, 번호로 순서 표시가 맞는가
- [ ] 모바일(≤640px) : 1열, 좌우 스크롤이 생기지 않는가
- [ ] 5단계 카드 5개의 높이가 실제로 같은가(`align-items:stretch` + `min-height` 적용분)
- [ ] 약관·방침의 표가 좁은 화면에서 표만 스크롤되고 본문은 밀리지 않는가
- [ ] 탭 아이콘(파비콘) 표시 — 하드 리프레시 후 확인 (P1-2 교차 확인)

### 6-2. 콘솔·네트워크 (개발자도구)

- [ ] Console에 오류·경고가 있는가 (특히 랜딩과 로그인 게이트 진입 시)
- [ ] Network에 404 리소스가 있는가 (이미지·폰트·파비콘)
- [ ] `<head>` Elements에서 `rel=icon` 링크 태그 실제 유무 확인

### 6-3. 로그인 이후 (본인 계정 필요)

- [ ] 존재하지 않는 `?p=` 링크 → '프로젝트를 찾을 수 없습니다' + 목록 이동 버튼이 실제로 뜨는가
- [ ] 1시간 무활동 자동 로그아웃 → 세션 만료 안내 문구가 뜨는가 (탭을 껐다 1시간 후 재접속 경로도 함께)
- [ ] 두 계정 동시 녹음 잠금 + 녹음자 탭 강제 종료 후 35초 경과 시 잠금 해제
- [ ] 병합 모드에서 문제/보류 상태 포스트잇의 회색·not-allowed 처리
- [ ] 스냅샷 11개째 생성 시 가장 오래된 것 자동 정리
- [ ] docx를 Word로 열어 목차 업데이트 동작, PDF 다중 페이지 분할
- [ ] **모바일 실기기 구글 로그인** (iOS Safari / Android Chrome) — 명세서에서 본인이 최우선으로 꼽은 미검증 항목
- [ ] 문제 해제 시 투표가 삭제된다는 점에 대한 확인 절차가 있는가 (없으면 실수로 표를 날릴 수 있다)
