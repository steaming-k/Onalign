## 0. 요약

> ### ✅ 확정 (v28) : 익명 참여 폐지, 전원 구글 로그인 방식으로 간다
> v26에서 제기했던 질문(팀원 익명 참여 폐지가 의도한 방향인가)에 대해, 랜딩페이지를 로그인 전제로 다시 써달라는 이번 요청으로 답이 확인됐다. **이제부터 "참여자는 로그인 없이 이름만 입력"이라는 기존 전제는 폐기하고, "리더든 팀원이든 구글 계정으로 로그인해야 참여 가능"으로 문서 전체를 갱신한다.** 4장 차별점 1번, 11장 경쟁사 포지셔닝, 랜딩페이지 카피를 이번 버전부터 이 전제로 정리했다.

### 왜 (Why) — 문제와 근거
캠프 아이디어 회의에서 "문제 정의" 단계에 가장 많은 시간을 쓰고, 그마저도 서로 다른 말로 같은 문제를 가리키는 걸 못 알아채 회의가 길어지는 걸 직접 관찰했다. 근거는 세 겹이다 — 본인 관찰(1차), production blocking 등 심리학 이론(보조), 노션 동시편집 데이터 유실 경험(가장 구체적, 엔지니어링적 사실). 외부 회의 비용 통계(연 392시간, 67% 비생산적)와 캠프 KPT 회고 11개 팀 실제 사례로 추가 검증했다(10, 14장).

### 무엇 (What) — 지금 만들고 있는 것
5~15인 소규모 팀을 위한, **구글 계정으로 로그인해 참여하는** 퍼실리테이션 도구(v28부터 "로그인 없이"에서 전환). 의견 작성 → 문제 정리 → 우선순위 투표 → **회고(KPT)** → **문서화**까지 한 프로젝트 안에서 이어진다. 메인 경쟁자는 EasyRetro/TeleRetro이며, 이들과 달리 "아이데이션과 회고를 잇는다"는 게 가장 방어력 있는 차별점이다(3, 4장). "로그인 없음"은 더 이상 차별점이 아니게 됐다 — 대신 "링크 하나로 전원이 같은 흐름에 올라탄다"는 쪽으로 포지셔닝을 옮긴다.

### 어떻게 (How) — 지금까지 만든 것과 확정된 설계
- **구현 완료 (배포·검증 완료)** : 의견 작성(다중 보드, 병합, 보류함, 빈공간 클릭 생성), 문제 정리, 우선순위 투표, 회고 탭, 문서 탭(표준 4필드, docx/프롬프트 추출, 녹음→녹취록 반영·경합버그 수정), 정렬 기준 통일
- **구현 완료 (v29 — 배포 완료 확인)** : 구글 로그인, 팀원 로그인 필수화, 공유 링크(`?p=id`), 리더 권한 분리(STEP 배너·투표권 수정·프로젝트 삭제=오너 전용), 헤더 배지 통합 — **실제로 커밋·push되어 배포 완료.** 랜딩페이지도 fetch로 실사이트 반영 직접 확인함(13장)
- **구현 완료 (v33 — 기능 명세서 v3, 배포 반영 일부 확인)** : 랜딩 5단계 확장·OG 태그·약관/방침 페이지·푸터, 동시 녹음 방지(하트비트 기반), 녹음 일시정지/종료 구분, 녹음 언어 선택, 녹취록 인라인 편집, 프롬프트 추출 옵션 패널(프리셋 4종·포함 항목 체크박스·글자수·편집 미리보기), PDF 내보내기, 문서 스냅샷(상한 10개), docx 목차·푸터, 1시간 무활동 자동 로그아웃, 세션 만료 안내 — 상세는 13-14장
- **구현 완료 (v35 — 기능 명세서 v4, 실사용자 실측은 미완)** : 녹음 캡처 범위 마이크+탭/화면 오디오 확장(13-17장 설계 그대로 구현), 3단계 자동 폴백, 녹음 오디오 파일(.webm) 저장, 무활동 타이머-녹음 충돌 해소, 녹음 시작 확인 모달(프로젝트당 1회) — 상세는 13-18장. **단, `SpeechRecognition.start(합성트랙)`이 실전에서 실제로 동작하는지는 명세서 스스로도 미검증으로 표시**하고 있어 '구현 완료'는 코드 존재를 뜻할 뿐, 최상 단계 도달 여부는 별개 확인 대상이다

## 1. 문제 정의

**결론 : 문제는 "발언 부족"이 아니라 "서로 다른 말로 같은 문제를 가리키는 걸 못 알아챔"이다.**

- 출발점 : 시장조사가 아니라 캠프 아이디어 회의 관찰
  - 시간 대부분을 "문제 현상/문제 정의"에 씀
  - 상대 의도를 못 알아채 회의가 길어짐
- 기존 워크플로우("의견 → 병합 → 문제 정리")와의 정합성 확인
  - 원래도 "의도가 겹치는 의견을 눈에 보이게 모으는" 구조였음
  - 풀어야 할 병목은 "말 못 함"이 아니라 "수렴 안 됨"

**근거 축 3가지 (우선순위 순)**

1. **본인 관찰** (1차 근거) — 캠프 회의에서 직접 겪음
2. **외부 조사** (보조 근거) — 직장인 약 절반이 침묵, 원인은 두려움보다 무력감
3. **노션 동시편집 버그** (가장 구체적, 신규) — 같은 자리 동시 편집 시 데이터 유실 경험
   - 포스트잇마다 편집 영역 분리 → 동시 충돌 원천 차단
   - 심리학 이론과 무관한 엔지니어링적 사실, 논문 불필요

**+ 독립 설계 목표** : "재미있게" — 생산성 축과 무관, 10~11장 학술 근거로 정당화/반박 대상 아님

> **정확히 하자면** : 실제 구현은 완전 독립 저장이 아니라 "최신 상태 재조회 후 내 항목만 반영" 방식 — 충돌 확률을 낮추는 것이지 원천 차단은 아님. 과장 금지.

**가설 1 (재수정)**
> 포스트잇 분리 시 (a) 동시편집 데이터 유실 방지 [사실에 가까움] + (b) 의도 파악 실패로 인한 지연 감소 [검증 필요]

**남은 숙제** : 지금의 "병합"은 누군가 먼저 "같은 얘기다"라고 알아채야 작동 → "알아채지 못하는 순간" 자체는 못 없앰 (5장 이후 계속)

## 5. 신규 기능 설계 : 아이데이션 → 회고 연결

**결론 : "회고" 탭이 5번째 탭으로 상시 존재하고, 참여자 각자 KPT를 작성·완료하며, 완료할 때마다 그 사람 몫이 문서 탭에 반영된다. 우선순위 해결여부 체크는 토글로 켜고 끌 수 있다. (v18, 확정 — 5장 설계 완료)**

1. 탭 구성 : 의견 작성 → 병합 → 문제 정리 → 우선순위 결과 → **회고** (5개 탭 상시 노출, 이전 설계의 "완료 버튼으로 잠금 해제" 방식에서 단순화됨)
   - ⚠️ **v33 정정** : 실제 탭은 의견 작성 · 문제 정리 · 우선순위 결과 · 회고 · **문서** 5개이고, **병합은 독립 탭이 아니라 의견 작성 탭 안의 모드**다 → 13-16장
2. 회고 포맷 : KPT (Keep-Problem-Try), 참여자 수만큼 입력 칸 제공 — **누가 작성했는지 이름과 함께 표시** (실명, 병합/문제 등 다른 기능과 일관된 방식)
3. "완료" 버튼 : **참여자 개인 단위** — 팀 전체를 기다리는 게이트 없이, 각자 자기 KPT를 다 쓰면 자기 버튼만 누름 → 그 사람 몫이 "과정 문서"와 "결과 문서" 양쪽에 반영됨. 완료 후에도 **잠금 없이 자유롭게 재수정 가능**
4. **우선순위 해결여부 체크 (토글, 확정)** : 회고 탭 상단에 ON/OFF 토글 스위치
   - ON : 아이데이션 우선순위 상위 문제 목록 + 해결됨/부분해결/미해결 체크 섹션이 참여자별 KPT 입력칸 위에 표시
   - OFF : 이 섹션 없이 KPT 입력칸만 표시
   - 기본값 : **ON** (핵심 차별점 요소이므로 기본 노출, 문제 정의로만 끝난 프로젝트는 팀이 직접 꺼서 숨김)
   - 토글 권한 : 참여자 누구나 (되돌리기 쉬운 화면 설정이라 리더 전용 아님)
   - 근거 : "이 회의가 문제 정의만 할 예정이었는지, 해결방안까지 도출하는지는 팀마다 다르다"는 판단 — 강제 노출이 아니라 선택 가능하게 둠

**의도적 제외** : 액션 아이템 담당자·마감일·Jira 연동 → ClickUp/monday 영역, 체급 밖

### 확정 이력

| 질문 | 결론 |
|---|---|
| 우선순위 문제 자동 표시 + 해결여부 체크를 회고 탭에 유지할지 | ✅ 유지, 단 ON/OFF 토글로 (기본 ON) |
| "완료" 버튼 권한 | ✅ 참여자 개인 단위, 팀 전체 게이트 없음 |
| "완료" 후 개별 KPT 재수정 가능 여부 | ✅ 잠금 없음, 언제든 자유 수정 |
| 프로젝트 상태(`진행중`/`완료`) 필드를 별도로 둘지 | ✅ 제외 — 완료가 개인 단위라 불필요 |

### 5-1. 문서 탭 표준 항목 추가 (v16, 신규)

**결론 : "과정 문서"·"결과 문서" 둘 다 목적/배경/추진방향/기대효과 4개 필드를 공통으로 갖고, 인라인 편집 가능해야 한다.**

| 필드 | 적용 대상 | 비고 |
|---|---|---|
| 목적 | 과정 문서 + 결과 문서 공통 | 인라인 편집 |
| 배경 | 과정 문서 + 결과 문서 공통 | 인라인 편집 |
| 추진 방향 | 과정 문서 + 결과 문서 공통 | 인라인 편집 |
| 기대 효과 | 과정 문서 + 결과 문서 공통 | 인라인 편집 |

- 기존 콘텐츠(과정 문서 : 개요·참여자·의견모음·문제정리 / 결과 문서 : 개요·우선순위 TOP5)는 이 4개 필드 아래에 이어지는 구조로 배치
- **내보내기 형식(v23 변경)** : HTML 다운로드 → **docx(Word) 다운로드**로 교체. 마크다운/이미지 내보내기는 유지. 이 4개 필드는 세 형식 전부에 포함
- 4개 필드는 프로젝트 단위로 한 번만 입력하면 과정/결과 문서 양쪽에 동일하게 반영 (별도로 두 번 입력하지 않음)

### 5-3. 프롬프트 추출 기능 (v23, 신규)

**결론 : 문서 탭에 "AI 요약" 기능을 직접 만드는 대신, 사용자가 이미 쓰는 AI에 붙여넣을 프롬프트만 만들어준다 — 서버 비용 없음.**

- **배치** : "마크다운으로 다운로드" 버튼 옆에 "프롬프트 추출" 버튼 추가
- **동작** : 클릭 시 문서 표준 4필드(목적/배경/추진방향/기대효과) + 의견 모음/문제 정리(또는 결과 문서라면 우선순위 TOP) + **회의 녹취록**을 하나로 합치고, 맨 앞에 "다음 회의 자료를 바탕으로 정리된 문서를 작성해줘" 류의 지시문을 붙인 완성된 프롬프트 텍스트를 생성
- **출력 방식** : 클립보드 복사 버튼 (붙여넣어 바로 쓰는 용도이므로 다운로드보다 복사가 우선)
- **설명 가이드** : 버튼 근처에 짧은 안내 문구 필요 — 예 : "회의 녹취록과 문서 내용을 하나의 프롬프트로 만들어드립니다. 복사해서 ChatGPT·Claude·Gemini 등 사용하시는 AI에 붙여넣으면 정리된 문서를 받아볼 수 있습니다."
- **설계 원칙과의 일관성** : 이건 5-2장(녹음 기능을 Whisper 유료 API 대신 무료 Web Speech API로 최종 확정)과 같은 결의 선택이다 — AI 요약이라는 기능 자체는 제공하되, 그 연산 비용은 서버가 아니라 사용자가 이미 보유한 AI 계정으로 넘긴다. 이 프로젝트가 "무료로 최대한 간다"는 원칙을 로그인 이전 마지막 기능에서도 그대로 지킨 셈이다

### 5-2. 녹음 → 문서 보강 연동 (v16, 신규) — 무료 구현 가능성 검토

**결론 : 텍스트를 문서에 넣는 것 자체는 무료로 가능하다. 다만 무관한 두 가지 무료 티어 리스크가 있다.**

- 텍스트 이관 자체 : 추가 비용 없음. 텍스트는 용량이 작아 Supabase 무료 DB(500MB)로 충분
- ⚠️ **기기 커버리지 리스크** : Web Speech API는 Chrome/Edge 데스크톱에서만 안정적. iOS Safari 등 모바일 브라우저는 지원이 불안정하거나 미지원 — 참여자 일부 기기에서 녹음 자체가 안 될 수 있음
- ⚠️ **Supabase 무료 티어 운영 리스크(녹음과 무관, 프로젝트 전체에 해당)** : 7일간 DB 요청 없으면 프로젝트 자동 일시정지(2026년 기준 여전히 유효). 캠프 세션 사이 간격이 있는 사용 패턴이라 실제로 겪을 수 있음 — GitHub Actions 등으로 주기적 핑을 보내는 무료 우회책 존재
- **(v34 갱신) 캡처 범위 확장 결정** : 위 내용은 마이크 단독 캡처를 전제로 쓴 것이다. 화상회의 화면 공유 상황에서 상대방 발화가 마이크에 안정적으로 잡힌다는 보장이 없다는 문제가 확인돼, 마이크+탭/화면 오디오로 캡처 범위를 넓히기로 했다 — 설계·트레이드오프·미검증 항목은 13-17장 참고
- **(v35 갱신) 구현 완료, 실측은 별개** : 위 확장 설계가 기능 명세서 v4에서 실제 코드로 구현된 것을 확인했다 — 13-18장. 다만 `getDisplayMedia`는 자동화로 검증할 수 없어, 혼합 트랙 실시간 인식이 실전에서 되는지는 여전히 실사용자 확인 대상이다

### 5-4. 리스트 정렬 기준 정리 (v24, 신규)

**결론 : 세 화면(문제 정리 탭, 우선순위 결과 탭, 문서 출력)의 정렬 기준이 서로 다르게 필요하다. 하나는 버그 의심, 하나는 신규 결정.**

| 화면 | 원래 설계 | 현재 상태(보고됨) | 처리 방향 |
|---|---|---|---|
| 우선순위 결과 탭 | 득표순 내림차순, 1위 강조(7장 기능명세서에 이미 명시) | 작성순으로 보임 | ⚠️ **설계와 다르게 동작 — 버그 의심.** 새 결정이 아니라 원래 설계대로 고치는 작업 |
| 문제 정리 탭 | (정렬 기준 없었음) | 작성순 | **신규 결정 필요** : 득표수 내림차순 우선, 표가 없는 항목끼리는 "문제로 표시된 시점" 최근순으로 제안(확인 대기) |
| 문서 출력 | 없음 (각 탭 순서를 그대로 따른다고 암묵적으로 가정) | 미확인 | 결과 문서는 우선순위 결과 탭과, 과정 문서의 문제 정리 표는 문제 정리 탭과 동일한 순서를 따르도록 명시 |

⚠️ **확인 필요** : 문제 정리 탭에서 무표 항목끼리의 2차 정렬 기준을 "문제로 표시된 시점(최근순)"으로 제안했는데, 이게 맞는지, 아니면 "원본 포스트잇 작성 시점"이 더 나은지 확인 필요.

## 6. 계정 시스템과 데이터 영구 보존

> ⚠️ **v33 경고** : 이 장의 결론과 절충 해법은 **v28에서 폐기된 전제(참여자는 로그인 없이 이름만 입력) 위에 쓰여 있다.** 지금은 전원 구글 로그인이다(0장). 이 장은 '그때 이렇게 판단했다'는 히스토리로만 읽는다 → 13-16장

**결론 : "로그인 없음"과 "영구 기록"은 오너/참여자 역할을 나누면 둘 다 지킬 수 있다.**

- **충돌 지점** : "로그인 없음"=참여자 마찰 제거용. 이번 요청(영구 기록)=오너의 소유권·영속성 문제 → 다른 축
- **절충 해법**
  - 오너 : Google/GitHub 로그인, 계정에 프로젝트 귀속
  - 참여자 : 기존과 동일, 이름만 입력
- ✅ **확인 완료** : 참여자는 로그인 없이 링크 참여 유지. 리더가 프로젝트를 생성하고 링크를 공유하는 구조로 확정
- ✅ **구현 시점 확정 (v20)** : 로그인 기능은 **테스팅이 얼추 완료되는 시점**에 착수 예정. 지금은 의도적으로 미루는 것 — 6-1(리더/팀원 화면 분리), 수익화(무료 한도) 등 로그인에 종속된 항목들도 자연히 같은 시점 이후로 순연됨

### 6-1. 리더/팀원 권한 분리 (v26 — 2건 확정, 1건 남음)

로그인 착수와 함께 세부를 확정한다. UI 문구에 이미 "리더가" 라는 표현이 박혀 있던 항목(13-6)들을 실제 권한 체크로 승격하고, 그 외 항목은 이번에 새로 판단해 제안했다.

| 기능 | 권한 | 근거/상태 |
|---|---|---|
| 회의 녹음 시작/종료 | 참여자 누구나 | ✅ 기존 확정 (개인 선택 기능) |
| 회고 "완료" 처리 | 참여자 각자 자기 몫만 | ✅ 기존 확정 (5장) |
| STEP 안내 배너 편집 | **리더 전용** | ✅ 구현·검증 완료. UI 읽기전용 + DB 트리거로 이중 강제 |
| 1인당 투표권 수 조정 | **리더 전용** | ✅ 구현·검증 완료. 팀원에겐 숫자만 노출, 조정 UI 자체 없음 + DB 트리거 이중 강제 |
| 프로젝트 삭제 | **리더 전용** | ✅ **확정 (3차 명세서로 확인).** RLS+UI 양쪽 강제 구현됨 |
| 문제 정리 탭 문구 다듬기 | **참여자 누구나** | ✅ **확정 (3차 명세서로 확인).** 제안대로 구현됨 |
| 문서 표준 4필드 편집(목적/배경/추진방향/기대효과) | 참여자 누구나 (제안) | ⚠️ **여전히 미확인.** 3차 명세서 8장(문서)에 권한 열이 없어 확인 안 됨 — 다음 라운드에 확인 필요 |
| 포스트잇 작성/병합/문제표시/보류, 투표 참여, 프로젝트 목표 편집 | 참여자 누구나 (변경 없음) | 기존 그대로, 구현 확인됨 |
| docx/마크다운 다운로드, 이미지 저장, 프롬프트 추출 | 참여자 누구나 (변경 없음) | 읽기·내보내기 성격, 구현 확인됨 |

**권한 이중 강제 원칙 확인됨** : UI 숨김만으론 API 직접 호출 우회가 가능해서, 오너 전용 기능은 RLS 또는 트리거로도 항상 막는다는 원칙이 실제로 지켜지고 있음(명세서 "설계 원칙 메모" 확인) — 특히 `projects` 테이블의 `instructions`/`votes_per_user`는 RLS가 행 단위라 컬럼별 보호가 안 돼서, 트리거로 컬럼 단위 오너 검사를 추가한 것으로 확인됨.

**기술적 전제** : OAuth는 실제 도메인·백엔드·DB 필요 → Claude 아티팩트 환경 불가능 → **프로토타입에서 실배포 앱으로 전환 신호**

**구현 옵션 (난이도 낮은 순)** : Supabase Auth(DB 포함) > Clerk(UI 완제품, DB 별도) > Auth.js(자유도 높음, 조립 많음)

**수익화 (확정)**
- 계정당 무료 프로젝트 개수 제한(예 : 2개) → 초과 시 구독/건당 결제
- DB 설계 시부터 "사용자-프로젝트" 1:N이 아니라 사용자에 plan·사용량 필드 포함
- 정확한 숫자·가격은 보류 (데이터 없이는 추측) — 지금은 "구조만" 준비, Stripe 연동은 이후 결정

- **배포 검증 리스크 (v33 갱신, v35 재확인)** : 13-12에서 '로컬 완성 ≠ 배포 확인'을 교훈으로 남겼는데, v33에서 파비콘이 정확히 같은 형태로 재발했었다(명세서엔 교체 완료, 실배포엔 404). v35 재감사에서는 이 항목이 실제로 해소된 것을 확인했다 — 다만 이번에는 **로컬 워킹트리 자체가 origin과 커밋 히스토리가 갈라진 채로 남아 있어(13-18장 배포 상태), 같은 유형의 문제(로컬에서 됐다고 배포에도 반영됐다고 믿는 것)가 다음 push 시점에 다시 발생할 조건이 갖춰져 있다**

| 구분 | 내용 |

| 단점 | 숙련 퍼실리테이터·준비시간 필요(→온라인 경량화로 상당수 해소 주장 가능) |

### 10-4. 문서 반영 요약

| 대상 | 반영 내용 |
|---|---|
| 1장 | 캠프 관찰(1차) + production blocking(보조) |

## 11. 학술적 근거에 대한 반론과 한계

**결론 : 반박 가능한 지점이 최소 2곳(11-1, 11-3) 있고, 1곳(11-2)은 업계 관행 자체의 약점이다. 숨기지 않는다.**

### 11-1. Production Blocking은 EBS에서 다른 이야기

- Diehl&Stroebe(1987)는 **대면 회의** 전제 — 타이핑 방식은 "전자 브레인스토밍(EBS)" 별도 범주
- Dennis&Valacich(1993) : EBS는 production blocking 사실상 없음 (유리)
- **BUT** Dennis&Valacich(1999) : EBS 우위는 9명↑ 큰 그룹부터. 5~8명은 개인작업과 차이 없거나 미결론
- **BUT** Pinsonneault et al.(1999) : EBS 우위 자체가 "착시(illusion)"일 수 있다는 반박, 논쟁 진행 중

→ **함의** : 목표 사용자(5~15명) 중 5~8명 구간은 학계 미결론 영역. **가설 F는 "5~8명에서는 성립 안 할 수도 있다" 전제로 재작성 필요**

### 11-2. 회고 자체의 실증 근거가 얇음

- 회고는 압박 시 가장 먼저 부실화/생략되는 관행으로 반복 보고
- 게임형 회고 개선 시도의 효과 근거는 거의 없음
- 학생 팀 실증 연구 : 성찰 수준이 피상적

→ **함의** : 4장 차별점 5번이 "학계도 증명 못한 가정" 위에 있음. "회고를 더 잘하게"보다 "회고를 하긴 하게"(완료 전환율)에 먼저 집중이 현실적

### 11-3. 실명 공개 투표의 편향 위험 — 검토 후 실명 유지로 최종 확정 (v20)

- 닷보팅 : 명시 기준 없어 편향·위계·지배적 목소리에 왜곡 가능
- 공개 투표 : 다수/영향력자 쏠림 위험, 익명 투표 권고 다수

**반론(타당함)** : "이름 알아야 발언 가능한 거 아니냐" → 맞음. 완전 익명은 1장 핵심 기능(되묻기) 자체를 무너뜨림

**✅ 최종 결정 (v20)** : 절충안(진행 중 익명·종료 후 공개) 대신, **투표도 의견과 마찬가지로 상시 실명 공개로 확정**한다. 이유는 "누가 왜 투표했는지 궁금할 수 있다"는 것 — 1장부터 일관되게 써온 원칙(이름이 있어야 되물을 수 있다)을 투표에도 그대로 확장한 결정이다.

**인지하고 가는 트레이드오프** : 위에서 인용한 문헌대로, 실명 공개 투표는 다수 의견·영향력 있는 구성원 쪽으로 쏠리는 편향을 만들 수 있다는 지적이 실제로 있다. 이 프로젝트는 "편향 감소"보다 "사후 논의 가능성"을 우선순위로 택한 것이며, 이건 근거가 없어서가 아니라 **알면서 택한 트레이드오프**다. 가설 I는 별도 실험 대상에서 제외하고, "실명 투표에서 쏠림 현상이 실제로 얼마나 발생하는지"는 8장 지표(득표 분포 등)로 사후 관찰하는 정도로 남긴다.

### 11-4. 확실한 것 vs 불확실한 것

| 가정 | 확실성 |
|---|---|
| 대면 발언 순서 대기 → 생산성 저하 | 확실 (40년 검증) — 단, 우리는 디지털이라 그대로 적용 안 됨 |
| 디지털 동시작성, 5~8명에서도 효과 | **불확실** (11-1) |
| NGT 구조가 동등 참여 보장 | 비교적 확실 (단점 존재) |
| 회고가 팀에 도움 | **생각보다 약함** (11-2) |
| 실명 투표가 공정한 결과 | **반대 증거 있음 — 알면서 실명 유지로 확정 (11-3, v20)** |

**🚨 최우선 사항** : 0장 요약 참고 — 팀원 익명 참여가 폐지되고 전원 구글 로그인 필수로 바뀜. 의도한 방향인지 확인 필요.

**⚠️ 배포 상태 경고 (중요)** : 명세서 원문에 명시된 대로, 아래 항목들은 **로컬 코드는 완성됐지만 배포(git push)와 실사용자 계정 검증이 아직 안 된 상태**다 — 구글 로그인, 팀원 로그인 필수화, 공유 링크(`?p=id`), 리더 권한 분리, 헤더 배지 통합. 이 문서에서도 이 항목들은 "구현 완료"가 아니라 "로컬 완성, 배포 검증 대기"로 별도 표기한다(0장 참고). Supabase schema.sql은 이미 1회 실행되어 로그인·프로젝트 생성까지는 사용자가 직접 확인함.

**참여 흐름 자체가 바뀜** : 기존 "이름/닉네임 입력 화면"이 사라지고, 공유 링크(`?p=프로젝트id`)로 접속 시 로그인만 하면 구글 프로필 이름으로 자동 등록되는 방식으로 대체됨. 화면 구성이 "로그인 게이트 → 내 프로젝트(오너) 또는 공유 링크(팀원)"로 재편됨.

**6-1 권한 매트릭스 갱신** : 프로젝트 삭제(리더 전용)와 문제 정리 문구 편집(참여자 누구나) 확정 확인됨. 문서 표준 4필드 편집 권한만 아직 미확인 상태로 남음.

**5-4 정렬 기준 확정** : 정렬 통일 버그 수정 확인됨. 다만 "우선순위 결과" 탭의 동점자 2차 정렬(빠른 표시순)이 "문제 정리" 탭(최근 표시순)과 **의도적으로 반대 방향**이라는 게 명세서에 명시됨 — 왜 두 탭을 다른 방향으로 뒀는지 구체적 근거는 명세서에 없어, 필요하면 다음에 확인.

**5-2 녹음-문서 연동** : 과거 지적했던 경합(race condition) 버그 수정 확인됨.

**데이터 아키텍처 변경 확인** : `projects`가 예전엔 kv_store 안 JSON 배열이었는데, 오너 단위 행 권한 적용을 위해 **진짜 테이블로 이관**됨. RLS는 행 단위 제어만 가능해 컬럼별 보호(예 : `instructions`, `votes_per_user`만 오너 제한)가 안 되는 한계를, 트리거로 보완한 것으로 확인 — 이건 이 프로젝트 전체에서 가장 기술적으로 정교한 설계 결정 중 하나로 기록해둘 만함.

**그 외 신규 확인** : 포스트잇을 빈 공간 클릭만으로도 생성 가능(버튼 클릭 없이), 헤더의 이름·색깔점 배지가 중복 없이 하나로 통합됨.

### 13-17. 회의 녹음 캡처 범위 확장 결정 (v34, 신규)

> **✅ v35 상태** : 이 장은 v34 시점의 **설계 문서**다. 이 설계가 실제로 코드로 옮겨졌는지는 기능 명세서 v4로 확인됐다 — 13-18장 참고. 아래 '구현 착수 전 확인이 필요한 것' 표의 2·4·5·6번(하드 체크·UA 필터링·체크박스 안내·에코 경고)은 명세서 문구상 반영된 것으로 보이고, **1번(혼합 트랙 실시간 인식이 실제로 동작하는가)과 3번(macOS 탭 단위 지원 시점)은 명세서도 '자동화 검증 불가, 실사용자 확인 필요'로 그대로 남겨뒀다.**

**결론 : 마이크 단독 캡처를 마이크+탭/화면 오디오로 확장하기로 결정했다. 텍스트 변환 엔진은 무료 Web Speech API를 그대로 유지한다. 다만 핵심 동작 하나(혼합 트랙에 대한 실시간 인식)가 아직 스파이크로 검증되지 않은 상태에서 내린 결정이라, 검증에 실패해도 지금 동작보다 나빠지지 않도록 3단계 대응 수준을 함께 설계했다.**

**배경(왜 이 논의가 필요했는가)** : 13-4·15장에서 확정한 녹음 기능은 로컬 마이크만 잡는다. 화상회의 화면을 켜 두고 진행하는 세션에서는 상대방 음성이 스피커로 나가더라도 마이크가 그 소리까지 같이 주워 담는다는 보장이 없다 — 스피커·마이크 배치 같은 물리적 조건에 좌우된다(추정). 그 결과 녹취록이 사실상 '본인 발화만' 남을 위험이 있고, 이는 1장 핵심 문제(문서 탭 문구가 어떤 맥락에서 나왔는지 되짚기)를 회의 오디오 쪽에서도 풀려는 5-2장 취지와 어긋난다.

#### 결정 1 — 캡처 범위 : 마이크 단독 → 마이크+탭 오디오

- **방식** : `getUserMedia`(마이크)와 `getDisplayMedia({audio: true, video: true})`(탭/화면 오디오, video는 API 제약상 필수이므로 캡처 직후 비디오 트랙만 즉시 정지)로 각각 스트림을 얻고, Web Audio API(`AudioContext.createMediaStreamSource` 2개 → `GainNode` → `createMediaStreamDestination`)로 하나의 합성 트랙으로 섞는다.
- **기각한 대안 : '녹음 후 변환 버튼' 방식(배치 처리)** — 폐기했다. 근거는 검증 과정에서 확인한 사실이다 : Gemini 같은 외부 멀티모달 API에 파일 전체를 올리는 구조라면 배치 처리가 자연스럽지만, 무료 Web Speech API는 살아 있는 MediaStreamTrack이 있어야 동작한다(결정 2 참고). 그래서 저장된 파일을 재생해 다시 캡처하는 우회(`HTMLMediaElement.captureStream()`)가 필요해지는데, 이 API 역시 MDN 기준 "Limited availability, not Baseline"이라 검증되지 않은 위험을 하나 더 얹는 선택이 된다.
- **경쟁 서비스와 비교해 확인한 것(채택 근거는 아니고, 구조가 다르다는 참고)** : Otter/Fireflies류는 회의에 봇으로 참가해 오디오를 직접 받고, Harmony류는 OS 시스템 오디오를 잡는 네이티브 앱이고, Otter의 크롬 확장 프로그램은 확장 전용 API(`chrome.tabCapture`)를 쓴다 — 셋 다 '설치 없이 링크 하나로 참여'라는 이 프로젝트의 전제와 구조적으로 맞지 않는다. `getDisplayMedia`는 평범한 웹앱에서도 쓸 수 있는 대신, OS/브라우저의 공유 선택 UI와 '공유 중' 표시가 항상 뜬다는 제약을 그대로 받아들인다.

#### 결정 2 — 텍스트 변환 엔진 : 무료 Web Speech API 유지 (BYOK Gemini 채택 안 함)

- 대안으로 검토한 BYOK(사용자 자신의 API 키를 직접 입력하는 방식) — 참고한 'Every Record' 확장 프로그램은 Gemini 키를 `chrome.storage.local`에만 저장하고 개발자 서버로는 아무것도 보내지 않는 구조였다. 이 방식은 발화자 구분·다국어 지원 등에서 우위가 있지만, 다음 두 가지 이유로 이번 라운드에는 채택하지 않는다 : ① 사용자에게 API 키 발급이라는 추가 마찰을 요구한다 ② Gemini 무료 티어는 제출된 데이터가 제품 개선에 쓰이거나 사람이 검토할 수 있다고 구글이 공식 고지하고 있어서, 회의 녹음처럼 참여자 전원의 개인정보가 담긴 데이터를 그쪽으로 보내는 것은 이미 지적된 방침 공백(17-2장의 국외 이전·삭제 요청 항목)을 더 키우는 방향이다.
- 이 결정은 '무료 유지가 항상 더 낫다'는 확정이 아니라, '지금 시점에 BYOK로 옮길 만큼 이점이 마찰·리스크를 상회하지 않는다'는 조건부 판단이다. 참여자 규모가 커지거나 발화자 구분 요구가 실제로 확인되면 재검토 대상이다.

#### 3단계 대응 수준 (실시간 인식 성공 여부에 따른 결과 차등)

가장 큰 미검증 리스크는 `SpeechRecognition.start(track)` — 마이크 대신 지정한 트랙에 대해 인식을 돌리는 옵션 파라미터 — 가 혼합 트랙에도 실제로 동작하는가이다. MDN은 이 파라미터를 "Limited availability, not Baseline"으로 표시하고, 사전에 지원 여부를 확인할 표준화된 방법이 없다는 이슈도 W3C 스펙 저장소에 열려 있다(참고 자료). 이 불확실성을 안은 채로 결정을 내렸기 때문에, 검증에 실패해도 결과가 지금보다 나빠지지 않도록 '녹음 파일 저장'(신뢰도 높음, MediaRecorder 기반)과 '실시간 텍스트 변환'(신뢰도 불확실)을 서로 다른 신뢰 수준으로 분리해 설계했다.

| 단계 | 조건 | 결과 |
|---|---|---|
| 최상 | 탭 오디오 캡처 성공 + 혼합 트랙 실시간 인식 성공 | 상대방 발화까지 포함해 실시간 자막·녹취록에 반영 |
| 중간 | 탭 오디오 캡처는 성공, 혼합 트랙 인식은 실패/미지원 | 녹취록은 기존과 동일하게 마이크(본인 발화)만 남지만, **저장되는 오디오 파일에는 양쪽 소리가 다 들어 있어 나중에 재생·다운로드로 확인 가능하다** |
| 하한 | 브라우저가 탭 오디오 캡처 자체를 지원하지 않음(Safari 등) | 기존 마이크 단독 동작과 완전히 동일 — 퇴행 없음 |

#### 구현 착수 전 확인이 필요한 것(스파이크 우선순위, 확정 아님)

| 순위 | 확인 항목 | 확인되지 않았을 때의 영향 |
|---|---|---|
| 1 | `SpeechRecognition.start(mergedTrack)`이 실제로 동작하는가 | 최상 단계 자체가 성립하지 않을 수 있음 — 가장 큰 미검증 리스크 |
| 2 | 캡처 직후 `stream.getAudioTracks().length` 확인 후 자동 하한 전환 로직 | Firefox는 API는 있으나 오디오 트랙을 조용히 비워서 돌려준다 — 함수 존재 여부만으로는 지원 판단이 안 됨 |
| 3 | macOS에서 탭 단위 오디오 공유의 실제 지원 시점 확인 | 시스템 전체 오디오 캡처(Chrome 141+·macOS 14.2+)와 탭 단위 공유의 지원 시점이 다를 수 있어 혼동 위험 |
| 4 | UA 기반 사전 필터링으로 Firefox/Safari에서 탭 오디오 옵션 자체를 숨길지 결정 | 지원 안 되는 옵션을 노출하면, 사용자가 선택했는데 안 되는 혼란이 생김 |
| 5 | Chrome '탭 오디오 공유' 체크박스 기본 미선택 상태에 대한 안내 카피 | 체크를 안 하면 조용히 마이크만 잡히는데, 사용자는 이를 인지하지 못할 수 있음 |
| 6 | 헤드폰 미착용 시 에코·중복 캡처 경고 카피 | 스피커로 나온 상대 음성을 마이크가 다시 잡아 텍스트가 중복될 수 있음 |

#### 정책에 미치는 영향

> **도구 제약** : 이 세션은 Playwright 등으로 직접 렌더링·조작이 불가능한 환경이라, `WebFetch` 도구로 텍스트 콘텐츠만 원문 인용 방식으로 확인했다. 이 방식의 한계 두 가지 — ① `<link>` 태그(파비콘·canonical 등)는 HTML→마크다운 변환 과정에서 소실돼 원문으로 볼 수 없다(파일 자체의 존재 여부만 응답 코드로 확인) ② 404 응답은 에러로만 반환되고 본문(커스텀 404 페이지인지 기본 페이지인지)은 확인할 수 없다.

| 항목 | v33 시점 상태 | v35(이번) 확인 | 판정 |
|---|---|---|---|
| favicon-32.png / favicon-128.png | 이슈 리포트 P1-2, `/favicon.ico`·`/favicon.png` 모두 404 | 새 경로(`favicon-32.png`, `favicon-128.png`)로 응답 확인(이미지 콘텐츠로 확인됨), 기존 경로는 여전히 404 | ✅ 해소로 판단(단 `<link rel=icon>` 태그 원문 확인은 도구 제약으로 못 함) |
| app.html 메타 태그(P1-1) | description·canonical·OG·Twitter 전부 없음 | title만 있고 나머지 전부 없음, 동일 | 미해결 지속 |
| 국외 이전 고지(P1-3) | 법정 고지 항목 누락 | privacy.html에서 "해외 서버에 저장될 수 있음"(Supabase·Vercel 항목) 원문 확인 | ✅ 해소 확인. 단 정확히 언제 고쳐졌는지는 이 세션에서 확인 불가 |
| 방침 표준 항목 5개(P2-2) | 5개 전부 누락 | "정보주체 권리·행사방법" 1개만 확인, 나머지 4개(위탁 통지, 제3자 제공 별도동의, 보호책임자 직함, 외부 구제기관 안내)는 여전히 없음 | 1/5만 개선, 4개 미해결 지속 |

| 차별점 카드 1번 "4단계" 잔재(P2-1) | 히어로는 5단계로 고쳐졌으나 카드 본문만 4단계로 남음 | "의견→병합→문제 정리→투표" 문구 원문 재확인 | **3라운드(v33·v34·v35) 연속 미해결** |
| og:image 규격(P3-1) | onalign-logo.png(가로형 워드마크), 권장 비율과 다름 | og:image가 여전히 같은 파일 | 미해결 지속으로 추정(치수 재측정은 도구 제약으로 못함) |
| robots.txt(P3-2) | 없음 | 여전히 404 | 미해결 지속 |
| 문의처 개인 Gmail 노출(P3-3) | 개인 Gmail 노출 | privacy.html 문의처가 여전히 개인 Gmail 형태 | 미해결 지속 |
| landing.html 미배포 레거시 파일 | (v33 시점엔 존재 몰랐음, v4 명세서에서 처음 언급) | 실제 접근 시 404 확인 | 명세서 주장과 일치 확인 |

**이 표에서 배울 것** : "이번 라운드는 기능/버그에 집중했다"는 판단 자체는 합리적이다. 다만 P2-1(차별점 카드 4단계)처럼 수정 자체는 한 줄짜리인 항목까지 세 라운드째 손 안 대는 건 '우선순위가 낮아서'가 아니라 '매번 이 문서를 쓸 때만 발견되고 그 사이에는 잊힌다'는 패턴일 가능성이 있다(추정) — 다음 액션 11번으로 별도 격상한 이유다.

## 15. 이번 근거로 추가 제안하는 기능 (검토 필요)

**결론 : 신규 기능 3개 제안 — 확정 아님, 검토 요청.**

1. **보류함(파킹랏)** : "나중에" 태그로 미결 안건 별도 보관 — "미결 기록 누락" 대응
2. **프로젝트 목표 한 줄 고정** : 프로젝트 생성 시 목표 한 줄 입력→상단 고정 — "목표 미합의" 대응
3. **회의 녹음 → 텍스트 변환** — **구현 완료 (13-4 확인)** : 참여자 누구나 개인 선택으로 녹음 시작/종료. 계획 당시 Whisper 등 외부 STT + 서버리스 함수를 전제했으나, 실제로는 **브라우저 내장 Web Speech API**로 구현되어 실시간 자막 패널(임시 텍스트 회색 표시), 중복 문장·단어 정리, `.txt` 다운로드까지 포함됨. 녹음 중지 시 결과는 **문서 탭 "회의 녹취록"에 직접 반영** (최초 계획했던 "포스트잇으로 저장"이 아니라 5-2장 목적대로 문서 보강으로 최종 확정)
   - **목적 재확인** : 발화자 구분이 아니라 "문서 탭 요약 문구가 어떤 맥락에서 나왔는지" 되짚을 원본 자료 확보 — 1장 핵심 문제(의도 파악 실패)를 보강하는 방향으로 판단
   - **권한** : 프로젝트 참여자 누구나 시작 가능 (리더 전용 아님) — 확정됨
   - **비용 구조 (수정)** : 서버·외부 API 없이 브라우저에서 완결 → 비용 없음. **"유료 플랜 전용 기능" 후보였던 수익화 근거는 소멸** — 6장 수익화 논의에서 이 항목 제외
   - **새로 생긴 제약** : Chrome/Edge 한정 (Web Speech API 브라우저 지원 범위), 브라우저가 인식을 자동 종료시킬 때 재시작 로직 필요 — 권한 거부·미지원 브라우저 예외 처리는 이미 구현됨(17장 정책과 일치)
   - **(v34) 캡처 범위 확장 설계 확정, 구현 대기** : 위 구현은 마이크만 잡는다. 마이크+탭/화면 오디오로 넓히는 설계를 확정했으나 아직 코드로 옮기지 않았다 — 3단계 대응 수준과 미검증 항목은 13-17장 참고
   - **(v35) 구현 완료, 실사용자 실측은 별개** : 위 확장 설계가 실제 코드로 구현됐다(마이크+탭 오디오 혼합, 3단계 자동 폴백, .webm 파일 저장) — 13-18장. 다만 화면공유 선택 UI가 필요해 자동화 검증이 안 되므로, 최상 단계(혼합 트랙 실시간 인식)가 실전에서 동작하는지는 여전히 확인 전이다

→ 셋 다 7장 MVP 표에 반영 완료 (1, 2번은 Should 대기, 3번은 구현 완료 + v35 확장 구현 완료·실측 대기)

### 17-1. 로그인·회고·문서화 이후 전체 사이트 재감사 (v32, 신규)

로그인·투표·회고·문서화 기능이 실제로 붙은 뒤, 전체 페이지를 다시 훑어 새로 발견한 엣지케이스다. **v33 시점 기준으로 11건을 다시 분류하면 처리 6건 / 확인 결과 문제가 아니었던 것 3건 / 다르게 결정된 것 1건 / 미검증 1건이다 — 아래 표 뒤에 따로 정리했다.**

| 영역 | 케이스 | 문제 소지 | 제안 정책 |
|---|---|---|---|
| 공유 링크 | 삭제됐거나 존재하지 않는 프로젝트 ID로 접근 | 빈 화면·크래시로 보일 수 있음 | "프로젝트를 찾을 수 없습니다" 안내 화면 + 목록으로 이동 버튼 |
| 로그인 | 팝업 차단기로 구글 로그인 창이 안 뜸 | 사용자가 아무 반응 없다고 오인 | 팝업 차단 감지 시 안내 메시지 표시 |
| 로그인 | 구글 토큰 만료 후 API 호출 | 조용히 실패하거나 무한 로딩 가능 | 인증 만료 감지 시 "다시 로그인해주세요" 안내 + 재로그인 유도 |
| 로그인 | 모바일 브라우저의 OAuth 리다이렉트 | 데스크톱과 동작 방식이 다를 수 있음 | 실기기 테스트로 확인 필요(가장 우선) |
| **우선순위 결과** | **오너가 회의 중간에 투표권 수를 줄임(예 : 5→2)** | **이미 투표한 사람의 잔여 투표권이 음수가 될 수 있음** | 기존 투표를 초과분만큼 자동 취소하거나, 잔여 투표권을 0으로 하한 고정(음수 표시 금지) |
| 우선순위 결과 | "문제 해제"된 항목에 이미 있던 투표 | 표가 사라지는지 남는지 불명 | 문제 해제 시에도 투표 데이터는 보존(재등록 시 복원)하되 집계에서만 제외 |
| 의견 작성 | 병합 시도 중 상대가 그중 하나를 동시 삭제 | 동시성 충돌 | 병합 실행 시점에 대상 포스트잇 존재 여부 재확인, 없으면 그 항목만 제외하고 병합 |
| 의견 작성 | "문제로"/"보류" 상태 포스트잇의 병합 대상 포함 여부 | 정책 불명확 | 문제/보류 상태는 병합 선택 대상에서 제외 제안 (상태 있는 항목은 이미 "정리된" 것으로 간주) |
| 프로젝트 관리 | 오너가 프로젝트 삭제 시, 보고 있던 다른 참여자 화면 | 폴링 중 데이터가 갑자기 사라짐 | 삭제 감지 시 "이 프로젝트는 삭제되었습니다" 안내 후 목록으로 이동 |
| 문서 | 스냅샷 무제한 생성 | Supabase 무료 저장공간(500MB) 소모 | 프로젝트당 스냅샷 개수 상한 설정, 또는 오래된 스냅샷 자동 정리 안내 |
| 회고 | 회고 탭 진입 후 새 참여자 합류 | KPT 입력칸이 즉시 생기는지 불명 | 참여자 목록 변경 시 회고 탭도 실시간으로 새 칸 추가되도록 확인 |

**우선순위 제안(v32 당시)** : 이 중 굵게 표시한 '투표권 하한 문제'와 '모바일 OAuth 확인'이 실사용에서 가장 먼저 부딪힐 가능성이 높아 보인다.

#### v33 처리 상태 (기능 명세서 v3 대조)

| 케이스 | 상태 | 실제 구현 방식 |
|---|---|---|
| 존재하지 않는 프로젝트 ID 접근 | ✅ 처리 | 안내 화면 + 목록 이동 버튼. **추가로**, 네트워크 오류를 '없음'으로 단정하지 않고 재시도 여지를 남기는 처리까지 들어갔다(제안보다 한 단계 정확함) |
| 팝업 차단으로 구글 로그인 창 안 뜸 | ➖ 해당 없음으로 정리 | 팝업이 아니라 **전체 페이지 리다이렉트(PKCE)** 방식이라 팝업 차단과 무관하다. 즉 제안한 정책이 아니라 **케이스 자체가 성립하지 않는다** — 제안 당시 구현 방식을 확인하지 않고 세운 케이스였다 |
| 구글 토큰 만료 후 API 호출 | ✅ 처리 | '세션 만료 안내' — 직접 로그아웃과 예상 못 한 세션 소멸을 구분해 안내 |
| 모바일 브라우저 OAuth 리다이렉트 | ⬜ 미검증 | 코드상 데스크톱과 경로 차이 없음까지만 확인. **v32에서 최우선으로 꼽은 항목이 그대로 남았다** |
| 오너가 회의 중 투표권 수 축소 | ✅ 이미 설계돼 있었음 | 재점검 결과 기존 투표는 유지, 화면 표시는 `Math.max(0, ...)`으로 하한 0. **v32에서 '음수 가능'으로 지적한 것은 코드 확인 없이 세운 가설이었고, 기각됐다** |
| 문제 해제된 항목의 기존 투표 | ⚠️ 다르게 결정됨 | 제안은 '투표 보존, 집계만 제외'였으나 구현은 **표 삭제(재등록 시 복원 없음)**, 의도된 설계로 명시됨. 더 단순한 쪽을 택한 것이라 그 자체로 문제는 아니나, **사용자에게는 '실수로 해제하면 표가 사라진다'는 뜻이므로 해제 시 확인 절차가 있는지 별도 확인이 필요하다**(미확인) |
| 병합 중 대상 동시 삭제 | ✅ 처리 | 남은 항목만으로 병합 진행 |
| 문제/보류 상태 포스트잇의 병합 대상 포함 | ✅ 처리 | 선택 대상에서 제외 + 반투명·not-allowed 커서로 이유를 보이게 처리 |
| 오너 삭제 시 다른 참여자 화면 | ✅ 처리 | 삭제 감지 후 안내·이동 |
| 스냅샷 무제한 생성 | ✅ 처리 | 상한 10개, 오래된 것부터 자동 정리 |
| 회고 탭 진입 후 새 참여자 합류 | ✅ 확인 결과 이미 정상 | `board.users`를 그대로 순회하는 구조라 다음 폴링(2초)에서 자동 반영. **별도 코드가 필요 없었다** |

> **이 표에서 배울 것** : 11건 중 3건(팝업 차단, 투표권 음수, 회고 새 참여자)은 **구현을 확인하지 않고 세운 케이스였고, 확인해보니 문제가 아니었다.** 엣지케이스를 넓게 던지는 건 여전히 유효한 방법이지만, '제안'과 '확인된 결함'을 같은 표에 섞어 두면 실제 작업량을 과대추정하게 된다 → 앞으로 이 표는 **제안 / 확인된 결함 / 확인 결과 문제 아님** 세 갈래로 나눠 쓴다.

### 17-2. 법적 문서와 제품 사이의 간극 (v33, 신규 / v35 일부 해소)

**결론 : 약관·방침이 배포되면서 '문서가 약속한 것'과 '제품이 할 수 있는 것'의 차이가 처음으로 실제 리스크가 됐다. 셋 중 하나(녹음 동의 확보)는 v35에서 구현이 확인됐고, 나머지 둘은 그대로 열려 있다.**

| 케이스 | 문서가 약속한 것 | 제품의 현재 상태 | 제안 |
|---|---|---|---|
| 개인정보 삭제 요청 | 보유기간 = '계정 삭제 또는 프로젝트 삭제 시까지', 권리 행사 = 이메일 요청 | **계정 삭제(탈퇴) 기능 없음.** 프로젝트 삭제는 오너 전용이라 참여자는 자기 콘텐츠를 스스로 지울 수단이 사실상 없다. v35 기능 명세서에도 변경 언급 없음 — 미해결 지속 | 단기 : 방침 문구를 실제 가능한 범위로 수정 + 이메일 요청 수신 시 수동 삭제 절차를 메모로 남긴다. 중기 : 계정 삭제 기능(프로필·본인 작성 콘텐츠 처리 정책 포함) |
| 녹음 동의 확보 | 약관 제7조 : 녹음 시작자가 참여자 전원 동의를 확보할 책임 | ✅ **v35 구현 확인** : 녹음 시작 버튼에 1회 확인 모달 추가됨(`board.recordingConsentAck`, 프로젝트당 1회, 탭/화면 오디오 옵션을 켜고 시작할 때만 노출). 배지는 '진행 중 고지', 모달은 '시작 전 확인'으로 역할 분리도 그대로 구현됨. 다만 **'프로젝트당 1회만 뜨는지'는 명세서 스스로도 미검증으로 남겨둠**(13-18장) | (해결됨 — 실사용자 확인만 남음) |
| 오너 계정 이탈 | 방침·약관 모두 언급 없음 | 17장 기존 제안(오너 이탈 시 읽기 전용 전환)은 미구현 | 로그인이 실제로 붙은 지금은 가상의 케이스가 아니다. 다만 발생 빈도가 낮아 **우선순위는 위 두 건보다 뒤**로 둔다 |

## 19. 문서화·녹음·프롬프트 추출 고도화 제안 (v30, 무료 범위 내)

**결론 : 셋 다 서버 비용·유료 API 없이 더 밀어붙일 여지가 있다. 우선순위 3단계로 나눈다.**

> **✅ v33 상태** : 이 장의 제안 **10건 전부가 기능 명세서 v3에서 구현 확인**됐고, 19장에 없던 신규 항목 2건(자동 로그아웃·세션 만료 안내)이 더해졌다. 항목별 대조와 '제안보다 더 들어간 부분'은 13-14장에 정리했다. 다만 19-2장이 겨냥한 '프롬프트가 너무 길어 붙여넣지 못하는 문제'는 완화만 확인됐고, 실제 AI 채팅창 한도에 걸리는지는 검증되지 않았다. 아래 표는 제안 당시 기록을 그대로 남긴다.

전제 : 이 장의 모든 항목은 클라이언트 코드 또는 기존 무료 API(Web Speech API 등) 범위 안에서 구현 가능하다는 것을 확인하고 제안한 것들이다 — 유료 API·서버 비용이 필요한 항목은 의도적으로 제외했다.

### 19-1. 우선순위 1 (버그성, 우선 처리)

| 항목 | 내용 |
|---|---|
| 동시 녹음 충돌 방지 | 참여자 누구나 녹음 가능(기존 확정)은 유지하되, 이미 녹음 중일 때 다른 사람의 시작 버튼은 비활성화 |

### 19-2. 우선순위 2 (체감 효과 가장 큼)

| 항목 | 내용 |
|---|---|
| 프롬프트 템플릿 선택지 | "정리된 문서로" 외에 "액션 아이템만", "슬랙 공유용 짧은 요약", "경영진 보고용 formal 톤" 등 프리셋 2~4개 버튼 — 지시문 텍스트만 교체, 비용 없음 |
| 포함 항목 체크박스 | 프롬프트 추출 시 회의 녹취록·완료된 회고 등을 포함할지 선택 — 프롬프트가 너무 길어져 AI 채팅창에 못 붙여넣는 문제 완화 |

### 19-3. 우선순위 3 (여유 될 때)

| 항목 | 내용 |
|---|---|
| PDF 내보내기 | jsPDF 등 클라이언트 전용 라이브러리로 서버 비용 없이 추가 |
| 문서 스냅샷(버전 고정) | "이 시점으로 고정" 버튼 — 클라이언트에서 JSON 스냅샷 별도 저장. 예전 PM 역질문에서 물었던 "특정 시점 확정본을 남길 방법" 질문에 대한 답 |
| docx 서식 보강 | 목차(TOC), 생성일자 푸터 추가 |
| 녹음 언어 선택 | Web Speech API `lang` 파라미터 교체만으로 가능 |
| 일시정지 vs 완전 종료 구분 | 회의 중 짧은 중단은 이어서, 끝나면 문서 반영으로 명확히 분리 |
| 회의 녹취록 인라인 편집 | 오탈자·오인식 교정 가능하게 — 문서 표준 4필드와 동일한 편집 패턴 재사용 |
| 프롬프트 복사 전 미리보기 + 글자 수 표시 | 불필요한 부분 미리 제거 가능하게, 길이 제한 있는 AI 채팅창 대비 |

### 19-4. 우선순위 0 — 녹음 캡처 범위 확장 (v34 신규 설계 → v35 구현 완료, 실측 대기)

기존 19-1·19-2·19-3은 전부 '이미 구현된 기능을 다듬는' 항목이었다. 이번 항목은 유일하게 **기존 동작 자체를 바꾸는(마이크 단독 → 마이크+탭 오디오)** 제안이라 별도 우선순위로 뺐다. 상세 설계·기각한 대안·3단계 대응 수준·스파이크 우선순위는 13-17장, 실제 구현 확인은 13-18장에 정리했고, 여기서는 다른 19장 항목과 같은 표 형식으로 상태만 갱신한다.

| 항목 | 내용 | v35 상태 |
|---|---|---|
| 탭/화면 오디오 캡처 추가 | `getDisplayMedia({audio:true, video:true})` + `getUserMedia`를 Web Audio API로 혼합해 단일 트랙 생성. video 트랙은 캡처 직후 중지 | ✅ 구현 확인 |
| 혼합 트랙 실시간 인식 시도 | `SpeechRecognition.start(mergedTrack)` — 실패 시 마이크 단독 인식으로 자동 대체 | ✅ 코드 구현 확인, ⬜ 실동작 여부는 실사용자 확인 필요(자동화 불가) |
| 녹음 파일 저장은 항상 유지 | MediaRecorder는 인식 성공 여부와 무관하게 혼합 트랙을 그대로 저장 — 실시간 텍스트화가 실패해도 사후 재생·다운로드로 양쪽 음성 확인 가능 | ✅ 구현 확인, `.webm` 다운로드 버튼까지 포함 |
| 지원 브라우저 사전 필터링 | UA 기반으로 Firefox/Safari 등에는 탭 오디오 옵션 자체를 숨기는 안내 | ✅ 구현 확인 |
| 녹음 시작 확인 모달 | 캡처 대상 확장에 맞춰 17-2장 정책과 함께 구현 — 이 항목만 정책(17-2장)과 기능(19-4)에 동시에 걸려 있다 | ✅ 구현 확인, 프로젝트당 1회 노출은 실사용자 확인 필요 |
